# Requirements - Identity (IDN)

Status: DRAFT · Service: [identity](../05-services/identity/README.md)

Line format: `REQ-ID · priority · inv: <invariants> · verify: <methods> · statement`

- **REQ-IDN-001** · MUST · inv: INV-IDN-001 · verify: model, type, e2e · Accounts are created only by an administrator invitation (or the one-time first-admin seed command). There is no public sign-up. An account becomes Active only when its owner sets a password through a valid setup link.
- **REQ-IDN-002** · MUST · inv: INV-IDN-002 · verify: model, prop, unit · Setup, invite and reset links are single-use, expire, are bound to one account and a nonce, are stored only as hashes, and a reused, expired or superseded link is rejected with the same response. Reset confirmation is throttled and applies the password rules (answers X1-017).
- **REQ-IDN-003** · MUST · inv: INV-IDN-003 · verify: type, unit · Passwords are hashed with Argon2id and checked against a documented minimum length and a deny list. Secrets (passwords, tokens, TOTP seeds, signing keys) have no `Display` or `Debug` implementation and cannot be logged.
- **REQ-IDN-004** · MUST · inv: INV-IDN-004 · verify: model, e2e · TOTP enrolment is two-step (set up, then confirm with a valid code). When an account requires TOTP, no authenticated session exists until the second factor succeeds.
- **REQ-IDN-005** · MUST · inv: INV-IDN-005 · verify: model, prop, unit · A TOTP code is single-use: once a time step has been accepted for an account, the same step and earlier ones are rejected, so a captured code cannot be replayed. Failed codes are counted per account.
- **REQ-IDN-006** · MUST · inv: INV-IDN-006 · verify: e2e, unit · Disabling TOTP, revealing a TOTP secret and changing the password require re-authentication (password, and a code when TOTP is on) (answers X1-017).
- **REQ-IDN-007** · MUST · inv: INV-IDN-007 · verify: model, prop, e2e · Sessions are opaque server-side tokens, hashed at rest, carried in an HttpOnly SameSite cookie, with idle and absolute expiry. Logout, suspension, disablement, deletion and password change revoke the affected sessions immediately.
- **REQ-IDN-008** · MUST · inv: INV-IDN-008 · verify: prop, e2e · Sign-in, reset request, reset confirm, invite acceptance, TOTP verify and resend endpoints are throttled per account and per address and return indistinguishable responses for known and unknown accounts (no enumeration) (answers X1-017).
- **REQ-IDN-009** · MUST · inv: INV-IDN-009 · verify: model, unit · Account status transitions follow Invited -> Active <-> Suspended -> Disabled; no other transition exists; every transition is audited and emits an event.
- **REQ-IDN-010** · MUST · inv: INV-IDN-010 · verify: type, model · The roles are exactly `reader`, `operator`, `admin`, stored once per user in identity. No role, flag or grant is a wildcard: `is_staff`, `is_superuser` and `admin:full_control` do not exist (answers X1-008). Role scopes (D-45): operator = reader scopes + `operate` + `manage_catalog`; admin = reader scopes + `manage_users` + `manage_catalog`; `download` and `read_once` are never role scopes, only grants.
- **REQ-IDN-011** · MUST · inv: INV-IDN-011 · verify: type, db · The scopes are exactly `browse`, `preview`, `read`, `read_once`, `download`, `kindle`, `operate`, `manage_catalog`, `manage_users`; `preview` and `read` are separate scopes and the reader role has both by default (D-41). A grant is an explicit row (user, scope, optional book, optional expiry, granted_by, reason); the database rejects an unknown scope, a book on a scope that is not book-scopable, and a duplicate active (user, scope, book) (answers X1-034).
- **REQ-IDN-012** · MUST · inv: INV-IDN-012 · verify: model, e2e, db · Only an admin (`manage_users`) creates, edits (expiry, active flag) or revokes grants and roles; never for oneself; several scopes of one user are granted or revoked in one atomic batch request (D-54), all or none; every change is audited in the same transaction; an admin cannot demote or disable the last active admin (answers X1-061).
- **REQ-IDN-013** · MUST · inv: INV-IDN-013 · verify: model, type · Authorization is deny-by-default. `decide(subject, scope, book?, book_state?, now)` is total and returns `Allow` or `Deny(reason)`; there is no code path in any service that authorizes without calling identity `/internal/authorize` or `/internal/check` (answers X1-001, X1-008).
- **REQ-IDN-014** · MUST · inv: INV-IDN-014 · verify: model, prop · Anonymous subjects can use only the closed list of public routes (sign-in, invite acceptance, password reset request and confirm, catalog metadata browse, search and detail with covers and summaries; D-34). They can never see preview text, read full text, download, send to Kindle or perform a management action (answers X1-006).
- **REQ-IDN-015** · MUST · inv: INV-IDN-015 · verify: model, prop, e2e · Reading full text requires an authenticated Active account and the `read` scope (role default or explicit grant, optionally for one book). Ownership, importing a book, "My Books" and shelves never grant access (answers X1-001, X1-058). The default policy of a new reader (`browse`, `preview`, `read`, `kindle`; `download` and `read_once` only by explicit grant) is configuration, not code (D-30).
- **REQ-IDN-016** · MUST · inv: INV-IDN-016 · verify: model, prop · The entitlement decision for a book takes its publication state from catalog and denies every state except `published` (and a soft-deleted book is never `published`) for subjects without `manage_catalog`; archived or withdrawn books stay inaccessible on every path (answers X1-009, X1-010).
- **REQ-IDN-017** · MUST · inv: INV-IDN-017 · verify: model, prop · Expired or revoked grants have no effect, evaluated against an injected clock; a disabled or suspended user is denied every scope.
- **REQ-IDN-018** · MUST · inv: INV-IDN-018 · verify: model, prop · Adding a grant never removes an existing permission (monotonicity). The only non-monotonic rule is read-once consumption.
- **REQ-IDN-019** · MUST · inv: INV-IDN-019 · verify: model, prop · Decisions do not depend on grant order and are deterministic for identical inputs.
- **REQ-IDN-020** · MUST · inv: INV-IDN-020 · verify: model, prop, e2e · Read-once allows exactly one redeemed reading ticket per account and book (counter per user and book, resettable by an admin). Identity verifies every reading ticket on every redemption through its internal `verify` call, which also re-checks the account state, the grant and the book's published state, so revocation is immediate; the reader never verifies a ticket signature itself (D-37). The opening is consumed when the ticket is redeemed for the book, not at open time and not when a file is missing; a reconnect or retry with the same ticket is not a new opening; no other action (download, preview) consumes it (answers X1-020).
- **REQ-IDN-021** · MUST · inv: INV-IDN-021 · verify: type, prop, fuzz · Reading tickets are opaque random values minted and stored (hashed) only by identity, valid at most 15 minutes, bound to user, book and version, carried in a header or body and never in a URL, and carry the grant version of the subject. The reader verifies every redemption by asking identity (D-37); there is no local signature check and no signing key; internal calls between services additionally carry an internal service token (answers X1-003).
- **REQ-IDN-022** · MUST · inv: INV-IDN-022 · verify: model, prop, e2e · Ticket redemption is idempotent for the same ticket; a ticket for another user, book or version, an expired ticket, or one issued before a `grant.changed` or `user.disabled` revocation is rejected. Honest limit: serving the whole book lets a reader copy it; controls are entitlements, short tickets, rate limits and an audit log of opens, not DRM (answers X1-003, X1-020).
- **REQ-IDN-023** · MUST · inv: INV-IDN-023 · verify: model, prop · Identity publishes `user.disabled` and `grant.changed` through its events outbox (`GET /internal/events?after=<cursor>`), written in the same transaction as the change; consumers apply each event idempotently from a stored cursor and tolerate duplicates and restarts.
- **REQ-IDN-024** · MUST · inv: INV-IDN-024 · verify: type, e2e · Every `/api/*` route of every service declares its required scope (or `public`) in code; a service whose route lacks a declaration refuses to start (fail closed). Identity `/internal/authorize` returns the verified user id and scopes as headers; services trust only those headers from the gateway and verify an internal service token on service-to-service calls (answers X1-002, X1-014).
- **REQ-IDN-025** · MUST · inv: INV-IDN-025 · verify: model, e2e · Management actions (`manage_users`, `manage_catalog`, `operate`) require a session that completed TOTP whenever the account requires TOTP.

REQ/INV-IDN-026 and 027 retired by D-35 (demo account dropped); other numbers are not reused.

- **REQ-IDN-028** · SHOULD · inv: INV-IDN-028 · verify: type, unit · A user may hold up to 5 Kindle addresses, each a validated `KindleEmail` newtype; only the owner can change them and only while holding the `kindle` scope (answers X1-042).
- **REQ-IDN-029** · MUST · inv: INV-IDN-029 · verify: db, e2e · Identity writes an append-only auth audit log in the same transaction as the change: sign-in success and failure, lockout, logout, reset request and confirm, password change, TOTP setup, confirm and disable, user create, invite, edit, status change, role change, grant create, change and revoke, reading ticket mint and redemption, profile image change, admin-reset use, with actor, subject, request id, address and a user-agent hash. No service role can update or delete rows; retention is 1 year (D-30, D-40). Audit scope across the system is set in REQ-PLT-009: auth, grants, roles, publish, unpublish, delete, operator actions, book opens and downloads (answers X1-084).
- **REQ-IDN-030** · MUST · inv: INV-IDN-030 · verify: e2e, unit · Identity returns one resolved capability set for the signed-in user (`/me/capabilities`); the web app derives navigation and route guards only from it, and the server remains the authority. Status 401 means no valid session; 403 means denied and never ends the client session (answers X1-014, X1-090).
- **REQ-IDN-031** · MUST · inv: INV-IDN-031 · verify: e2e, review · Admin user administration lists users with bounded pagination and search, resends setup links (superseding old ones), and deletes an account on request; a user can export their own identity data as JSON (`GET /me/export`, D-30; the Settings screen bundles it with the reader and catalog exports, D-55). Deleting an account announces it to the services that hold user-owned data so they erase it (answers X1-041).
- **REQ-IDN-032** · MUST · inv: INV-IDN-032 · verify: review, e2e · No seed, test or advance endpoint is compiled into production builds. The first admin is created by a one-time command that refuses to run when an admin exists, has no default password and defaults to dry-run (answers X1-005, X1-023).
- **REQ-IDN-033** · MUST · inv: INV-IDN-033 · verify: e2e, review, static · The only recovery path for a locked-out admin is the documented host command `admin-reset` of identity, run on the host by someone with host access; there is no break-glass account, no hidden credential and no two-person approval. The command is audited, defaults to dry-run and sets a one-time setup link rather than a password. The rules stay: an admin cannot change their own role or status and cannot demote or disable the last active admin (D-38, REQ-IDN-012).
- **REQ-IDN-034** · MUST · inv: INV-IDN-034 · verify: type, unit, e2e, fuzz · Profile image upload is kept (D-44): identity accepts only an allow-listed image type (SVG refused) up to a configured size limit, re-encodes or strictly validates it, stores it, and serves it only through identity to its owner and to admins; it is never public and never part of a public route, and deleting the account deletes the image (X1-004).
