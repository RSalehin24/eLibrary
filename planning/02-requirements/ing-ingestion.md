# Requirements - Ingestion (ING)

Status: DRAFT · Service: [ingestion](../05-services/ingestion/README.md)

Scope (new-architecture section 6, D-03, D-31, D-32): one pipeline - source mirror sync, request, scrape, curate and validate, duplicate review, EPUB build, publish to catalog automatically when every gate passes (D-49) - run by an API container and a worker container over a Postgres job queue. Intake is scrape-only; there is no manual EPUB upload (D-42). The legacy submission, processing and curated-document paths are merged; nothing is migrated (books are re-ingested). Rules marked "kept from v1" carry v1 requirements unchanged in substance.

- **REQ-ING-001** · MUST · inv: INV-ING-001 · verify: model, db · There is one request model and one orchestrator: a request has an execution status and a separate domain outcome (built, needs_review, duplicate, failed, published; `submitted` was retired by D-49); `created` implies a book candidate exists; every terminal path restores the owning entity's state. (answers X1-025, X1-031, X1-106)
- **REQ-ING-002** · MUST · inv: INV-ING-002 · verify: db, prop · The source mirror (listing of the source site, incomplete tracking) and the local workflow state live in separate columns or tables: a re-sync writes only source-owned fields, never overwrites workflow state, and an empty or failed fetch is a no-op that resolves nothing. (answers X1-024, X1-026, X1-030)
- **REQ-ING-003** · MUST · inv: INV-ING-003 · verify: model, prop · Mirror sync is idempotent (creates no extra requests), tracks incomplete books, and runs as an explicit state machine whose every transition is tested against live-shaped fixtures. (answers X1-045; kept from v1, changed)
- **REQ-ING-004** · MUST · inv: INV-ING-004 · verify: model, prop, db · Jobs live in a Postgres `jobs` table claimed with `FOR UPDATE SKIP LOCKED` under a lease with heartbeat from the working thread only, a visibility timeout and an attempt counter; lease expiry moves only Running to Queued; at most one active job per request; completion is idempotent. (answers X1-065, X1-066, X1-055)
- **REQ-ING-005** · MUST · inv: INV-ING-005 · verify: type, e2e · No work runs inside an HTTP request: handlers only enqueue; when the queue is unavailable they return 503 or a queued result, and no inline fallback or test hook (environment sniffing) exists in production code. (answers X1-005, X1-067)
- **REQ-ING-006** · MUST · inv: INV-ING-006 · verify: type, unit · Failures are typed (`retryable`, `rate_limited` with retry-after, `auth_required`, `permanent`); retry is decided by the type, never by error text; backoff re-queues with a delay and never sleeps in a worker. (answers X1-046, X1-067)
- **REQ-ING-007** · MUST · inv: INV-ING-007 · verify: model, prop, e2e · Steps are idempotent and write new output before replacing old; a cooperative cancel flag is checked before every page fetch and between stages; long jobs (catalog refresh included) have page budgets, an error budget and real cancellation. (answers X1-068, X1-070)
- **REQ-ING-008** · MUST · inv: INV-ING-008 · verify: model, unit, e2e · Every operator action is guarded by an allowed-source-state table (invalid transitions return 409); bulk actions are bounded, idempotent and return per-item results; deletion of a book by a request never applies to a book the request did not create. (answers X1-033, X1-053, X1-064, X1-077)
- **REQ-ING-009** · MUST · inv: INV-ING-009 · verify: type, e2e · Every ingestion route declares its scope (`operate` for the pipeline) and records the actor; there are no anonymous or capability-by-UUID endpoints, and request reuse across users is never implicit. (answers X1-006, X1-018, X1-072)
- **REQ-ING-010** · MUST · inv: INV-ING-010 · verify: type, review · Acquisition is GET-only: the client type exposes only `get`, so no form submission or mark-complete is representable (D-03); fetches obey a host allow-list, an honest User-Agent with a contact address, a polite delay (default 0.5 s between pages), a concurrency cap, and never bypass TLS verification or use DNS or direct-IP fallbacks. (answers X1-012, X1-016; kept from v1)
- **REQ-ING-011** · MUST · inv: INV-ING-011 · verify: type, unit, e2e · The one source-site credential is a cookie read from a rotatable, read-only secret file; only its status and expiry are stored and shown on the console (valid, expiring, expired); it never appears in argv, logs, database or the browser. An `auth_required` failure points the operator to the credential status. (answers X1-015)
- **REQ-ING-012** · MUST · inv: INV-ING-012 · verify: db, drill · Scrape cache is stored as files (not in a row), keyed by request and freshness, resumable per page, and removed on terminal states or after 30 days; raw pages are retained 30 days. (answers X1-035, X1-073)
- **REQ-ING-013** · MUST · inv: INV-ING-013 · verify: db, prop · One authoritative curated document per request and run is written once and versioned; derived artifacts carry (source hash, ruleset version) and are regenerable; the whole book is never stored in a request row. (answers X1-027, X1-035; replaces v1 REQ-ING-001)
- **REQ-ING-014** · MUST · inv: INV-ING-014 · verify: prop · Conservation: every input block ends in exactly one output location or is recorded as dropped with a reason code; no block is lost silently. (kept from v1 REQ-ING-002)
- **REQ-ING-015** · MUST · inv: INV-ING-015 · verify: type, prop · Reading order is a total order over leaf sections; the in-book TOC, nav document and NCX are generated from the same tree; page order is Cover, Title, Book Info, Dedication, Front sections, TOC, Chapters, End sections, empty pages omitted. (kept from v1 REQ-ING-003)
- **REQ-ING-016** · MUST · inv: INV-ING-016 · verify: prop · With a source TOC, that TOC is authoritative: no chapter is invented or merged, nesting is preserved, a parent is never replaced by its children, and `/books/...` links are never chapters. (kept from v1 REQ-ING-004)
- **REQ-ING-017** · MUST · inv: INV-ING-017 · verify: prop, review · For single-page books chapters are inferred from headings, numerals and Bengali boundary patterns, and each inferred boundary carries evidence and confidence. (kept from v1 REQ-ING-005)
- **REQ-ING-018** · MUST · inv: INV-ING-018 · verify: model, prop · A book is built only if every TOC leaf was fetched or is recorded as empty at the source; one configured threshold is shared by classification and build, placeholders are not counted as fetched, and any omission caused by a limit is a validation error, never a silent drop. (answers X1-029, X1-047; kept from v1 REQ-ING-006)
- **REQ-ING-019** · MUST · inv: INV-ING-019 · verify: prop, review · Every extracted entity (title, writer, translator, editor, publisher, series, category, date, edition, dedication) carries evidence and confidence; below the ruleset threshold the item goes to review and nothing guessed is published. (kept from v1 REQ-ING-007)
- **REQ-ING-020** · MUST · inv: INV-ING-020 · verify: prop · A fact appears once: text promoted to Book Info is removed from front sections, a dedication is never also a front section, and residual text with no new information is dropped with a recorded reason. (kept from v1 REQ-ING-008)
- **REQ-ING-021** · MUST · inv: INV-ING-021 · verify: unit, review · Language is detected once, stored and overridable; labels, nav titles, Book Info keys and digit forms use that language only (no Bengali labels or digits on an English book). (answers X1-048; kept from v1 REQ-ING-009)
- **REQ-ING-022** · MUST · inv: INV-ING-022 · verify: unit, prop · Bengali-correct normalization has one entry point (NFC, nukta composition); rule and word tables are versioned data whose literals keep vowel signs and viram, are tested on the gold corpus held outside git, and matching is at token boundaries, never substring. (answers X1-046)
- **REQ-ING-023** · MUST · inv: INV-ING-023 · verify: prop, e2e · Duplicate matching uses the exact normalized title key plus author, category, edition and translators (a translator difference means a different book, `new_work`, never a duplicate or `needs_review`; D-92) from one indexed implementation; there is no fuzzy threshold, near-matches are listed for a human, and nothing is auto-merged. Duplicate review is an explicit state with the actions create new, create as new edition, confirm duplicate and discard; an exact duplicate is refused. (answers X1-049, X1-052; kept from v1 REQ-ING-015, changed)
- **REQ-ING-024** · MUST · inv: INV-ING-024 · verify: type, fuzz · The EPUB builder escapes all text it writes into XHTML and OPF (escaping on, never `safe`) and passes scraped chapter HTML through an allow-list sanitizer; the same builder version and curated document give a byte-identical EPUB. (answers X1-004; replaces v1 REQ-CON-002/009)
- **REQ-ING-025** · MUST · inv: INV-ING-025 · verify: prop, review · The EPUB packages every referenced image and embeds Noto Serif Bengali regular and bold, writes complete OPF metadata (stable identifier derived from book id and version, title, contributors with roles, language, date, publisher, series where known), and generates both the nav document and NCX. (answers X1-060)
- **REQ-ING-026** · MUST · inv: INV-ING-026 · verify: prop, review · A build is a candidate only after the gate passes: XML well-formedness, structure audit, epubcheck with 0 errors (run inside the ingestion worker before publish, D-47), and nav, NCX and TOC consistency; otherwise the request ends failed and no version is created. (kept from v1 REQ-CON-007, changed)
- **REQ-ING-027** · MUST · inv: INV-ING-027 · verify: type, prop · Cover images are fetched only from allow-listed hosts and validated by bytes; the generated fallback cover shows title and author with correct Bengali shaping. (answers X1-021)
- **REQ-ING-028** · MUST · inv: INV-ING-028 · verify: type, prop · The public preview is built at build time from an allow-list (metadata, summary, TOC, first N characters of the first chapter, N from D-05) and handed to catalog as a distinct artifact. (kept from v1 REQ-CON-003)
- **REQ-ING-029** · MUST · inv: INV-ING-029 · verify: model, e2e · Publishing calls catalog `POST /internal/books/{id}/versions` with the artifacts and an idempotent build identity; the version is published by that call with no human step (D-49); a retry after a crash yields one version, and a failed build never leaves a visible book. (answers X1-027; kept from v1 REQ-ING-016, changed)
- **REQ-ING-030** · MUST · inv: INV-ING-030 · verify: prop, review · Rulesets are versioned and promoted only if gold-set metrics do not regress; reprocessing creates a new version and shows a structured diff (sections, entities, text) before it replaces a published build. (kept from v1 REQ-ING-011)
- **REQ-ING-031** · MUST · inv: INV-ING-031 · verify: review, e2e · Intake is scrape-only in v1 (D-42): there is no manual EPUB or file upload and no route or command that accepts one; every curated document comes from the scrape pipeline. The only manual intervention is editing metadata (through the catalog's audited edit and review path).
- **REQ-ING-032** · MUST · inv: INV-ING-032 · verify: model, e2e · Console live updates use Server-Sent Events fed from an outbox with LISTEN/NOTIFY: heartbeat, `Last-Event-ID` resume, a versioned snapshot on reconnect, per-user filtering, and client backoff; state shown follows server-confirmed state only. (answers X1-071, X1-100)
- **REQ-ING-033** · MUST · inv: INV-ING-033 · verify: model, unit, e2e · Automation is a stored schedule with a `next_due` claimed under lock (one run per due slot), validated interval and time with an explicit time zone, defaults of 3 attempts per request and 50 requests per run, mutual exclusion with manual runs, and no automatic retry of duplicate or needs_review outcomes. (answers X1-051)
- **REQ-ING-034** · MUST · inv: INV-ING-034 · verify: db, drill · Retention is enforced by jobs: raw pages 30 days, job attempts and logs bounded, previous-version files kept until the next version is published, and cache cleanup on terminal states. (answers X1-088)
- **REQ-ING-035** · MUST · inv: INV-ING-035 · verify: db, e2e · Every state change and operator command appends an audit event with the actor; logs are structured and carry the job correlation id. (answers X1-084, X1-085)
- **REQ-ING-036** · MUST · inv: INV-ING-036 · verify: model, e2e · Publishing is fully automatic and gated (D-49): ingestion calls catalog publish only for a build that passed every gate (curated validation, structure audit, epubcheck with 0 errors in the worker per D-47, and the exact-key duplicate rule; if epubcheck cannot run the gate fails closed and nothing is published, D-57), and the book is then visible with no human step; any build that fails a gate is never sent to catalog and stays in the review queue (duplicate review, `needs_review` or `failed`) until an operator acts. (D-49)
