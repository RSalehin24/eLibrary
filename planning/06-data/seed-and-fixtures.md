# Seed data and fixtures

Status: DRAFT (D-32 fresh start; D-29 scale; D-03 GET-only; CLAUDE.md content rules)

There is no data migration (D-32): users are re-invited, books are re-ingested by the new pipeline, and the old data stays in `archive/` only. This file defines what data the new system starts with and what tests use. Rule: **no third-party book content and no gold corpus is ever committed**; all committed text is synthetic.

## 1. Synthetic seed data (development, e2e, load)

A test-only seed tool (a container or `xtask seed`, absent from production builds, REQ-IDN-032) fills the ephemeral stack:

| Set | Content |
|---|---|
| Users | one admin, one operator (with `operate` and `manage_catalog` per the unconfirmed D-45 table), several readers (default grants), one reader with `download`, one with `read_once`, one disabled user, one pending invite. Fixed passwords for local and e2e only, never a real credential |
| Books | small set (about 30) with invented titles, authors and Bengali and English text, covering: published, draft, archived, a build held in the review queue (failed gate), a book with two versions, a book with images and an embedded font, a book with a multi-page table of contents, a read-once book |
| Large set | generator for 5,000 books and the matching reading copies for load tests (REQ-NFR-003), invented text, deterministic seed |
| Reading state | bookmarks, highlights and notes for several users including after a version change |
| Source mirror | mirror rows for a synthetic source catalog, some missing locally, some incomplete |

The seed is deterministic (fixed random seed and fake clock), idempotent, and goes through the services' own APIs or contract-typed commands, never straight into another service's tables (data ownership).

## 2. Test fixtures

| Fixture | Used by | Notes |
|---|---|---|
| Source pages (`fixtures/source/`) | ingestion tests, e2e J4 and J8 | synthetic HTML in the structure shapes of the source site (flat, nested, sectioned, paginated TOC, single page, no headings, locked placeholder); a canary per shape detects drift; served by the `source-fixture` container with fault modes (see [strategy](../09-testing/strategy.md), [fault injection](../09-testing/fault-injection.md)) |
| EPUB samples | reader and builder tests | generated by the builder from synthetic documents, plus hand-made malformed, hostile (script, remote reference) and oversize EPUBs for sanitizer tests |
| Bengali normalizer cases | property and unit tests | synthetic term pairs with vowel signs and conjuncts; words from public-domain sources may be used only if their licence is recorded |
| Mail sink | notify and e2e | SMTP capture container, no real mail |
| Images and fonts | builder tests | small generated images; Noto Serif Bengali (SIL OFL) may be committed as the embedded font with its licence file |

Nothing recorded from the live source site is committed except, if a structure cannot be reproduced, a minimal excerpt that the owner has approved case by case. No test contacts the live site.

## 3. First-admin seed (production)

The first admin is created once by the identity host command `seed-first-admin` (REQ-IDN-032): dry-run by default, refuses when an admin exists, sets no password (it issues a one-time setup link), and is audited. Not an HTTP route; absent test and seed routes in production builds. The owner's email address is passed as an argument, never stored in the repository. Recovery later is the `admin-reset` host command (D-38).

## 4. Initial source import plan (launch)

Order after the stack is live and the owner has the source's permission (D-03, gate G6):

1. Place the source cookie in the read-only secret file (rotatable without a rebuild) and check the console status.
2. Run the catalog mirror sync (GET only) to fill the source mirror; review the mirror counts.
3. Pick a pilot batch of about 20 books, create requests, run the pipeline, resolve duplicate reviews, check the built EPUBs (in-worker audit and epubcheck, D-47), and confirm each passing book is published automatically (D-49), unpublishing any that is wrong.
4. Confirm reader copies exist and the published set matches (REQ-NFR-013); read two books on phone and desktop.
5. Import the rest in batches within the automation defaults (3 attempts, 0.5 s delay, 50 requests per run); locked chapters stay waiting for sanctioned access and are never submitted or bypassed.
6. Invite users (no migrated accounts), take the first full backup and run the restore drill (D-33).

Batch sizes, order and the review workload are provisional (OPEN until the P0 baseline). Planned launch steps belong in the launch runbook ([operations](../11-operations/backup-restore.md)); this section only states the data plan.

## 5. Not kept (D-32)

Legacy users, passwords, books, files, reading data, ETL and cutover are not migrated, and no migration test exists. The legacy repository stays read-only in `archive/` for reference.
