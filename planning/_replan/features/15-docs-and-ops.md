## 2. Operational behaviours

### 2.1 Runtime topology (compose, identical shape in deploy / local / local-production)
Services: `postgres:16-alpine`, `redis:7-alpine`, one-shot `backend-init` (`manage.py migrate` then `seed_superadmin`), `backend` (prod: migrate, collectstatic, seed_superadmin, gunicorn on 8000), `worker` (Celery queue `celery`), `processing-worker` (Celery queue `processing`, hostname `processing@%h`), `engine` (`manage.py run_engine`, long-running, internal network only, no storage mount in deploy), `beat` (Celery beat), `frontend` (nginx:1.27-alpine serving Vite build). Two networks: `public`, `internal` (internal: true). Backend and frontend ports are bound to 127.0.0.1 only; host nginx fronts them. All app containers get DNS 1.1.1.1 / 8.8.8.8 (prod). Postgres/Redis data in named volumes `postgres_data`, `redis_data`. App storage is a bind mount `app/backend/storage` -> `/app/storage` (prod/local) or a named volume `local_prod_storage` (local-production). Healthchecks: postgres `pg_isready`, redis `ping`, backend GET `/api/csrf/` (prod, local-prod) or `/api/health/` (local), all interval 5s/retries 20. Dependencies gated on `service_healthy` and `backend-init: service_completed_successfully`.
Dockerfile: `python:3.12-slim` + apt `fonts-noto-core`, `libraqm0` (needed for Pillow/raqm Bengali text rendering - cover generation); node 22-alpine build then nginx 1.27-alpine. Frontend nginx: hashed assets `expires 1y, immutable`; `index.html` `no-store`; SPA fallback to index.html.

### 2.4 Migration (server-to-server) phases and checks (`migration/migrate.sh`)
Config `migration/env/migrate.env`; inherits most values from `deploy/env/.host.env`. Keys: TARGET_IP (required), TARGET_USER, TARGET_REMOTE_APP_DIR, TARGET_PUBLIC_BASE_URL / API_ORIGIN / FRONTEND_BASE_URL overrides, SOURCE_PORT/TARGET_PORT (22), DRAIN_TIMEOUT_SECONDS 900, HEALTHCHECK_TIMEOUT_SECONDS 240, KEEP_SOURCE_DOWN_ON_SUCCESS 0, ALLOW_TARGET_RESET 0, SKIP_EDGE_SETUP 0, KEEP_STAGING (script default 1), STRICT_HOST_KEY_MODE (accept-new|yes|no), SOURCE/TARGET _SSH_KEY_PATH, _SSH_PASSWORD (needs sshpass), _SUDO_PASSWORD, BUNDLE_ID, LOCAL_STAGING_DIR. Flags: `--phase`, `--dry-run`, `--resume`, `--keep-staging`, `--allow-target-reset`, `--skip-edge`, `--config`.
Phase markers `.phase-<name>.done` in `migration/runtime/<bundle-id>/`; `--resume` takes the newest bundle dir and skips done phases.
- Preflight: local tools (bash ssh scp tar gzip python3 sha256sum|shasum); SSH both; timed 10 s "have you pointed the domain at the target IP?" prompt (non-blocking); OS must be ubuntu/debian; passwordless sudo; source layout files exist; source stack healthy (postgres, redis, backend must be healthy; frontend/worker/processing-worker/beat running; GETs to `/api/csrf/` and `/`); target ports BACKEND, FRONTEND, 80, 443 free; target dir state (missing/empty/resumable via `.migration-state/bundle-id`/resettable/occupied -> abort); disk: local needs 1.25x raw + 100 MB, target needs 2x raw + 100 MB (raw = app + storage + pg data + redis data); edge readiness (domain+certbot email set, DNS resolves to target IP).
- Snapshot: stop beat, frontend, backend; wait up to DRAIN_TIMEOUT for Celery `inspect` active/reserved/scheduled = 0 and Redis `celery` and `processing` list lengths = 0 (on timeout restart source and abort); then stop worker and processing-worker; copy source `.app.env`; stream app tar (no .git, storage, env, node_modules, logs); storage tar; Postgres = `pg_dumpall --globals-only` + `pg_dump --clean --if-exists --create` of the app DB, bootstrap-role lines stripped, gzip -1; Redis `SAVE` then cat `dump.rdb`; metadata manifest (source git commit, per-table row counts via pg_stat_user_tables, table count, row total, role count, sha256 of the sorted "table=count" list, Redis DBSIZE + queue lengths + used_memory, storage file count + total bytes, SHA-256 of each artifact); `checksums.sha256` verified locally.
- Restore: upload to `/tmp/<bundle-id>` on target, verify checksums remotely; wipe app dir if reset allowed; extract app; copy env then merge `target-env-overrides.env` (BACKEND_PORT, FRONTEND_PORT, optional public URLs) non-empty-only; install Docker; `compose down --volumes` then start postgres+redis; restore SQL with `ON_ERROR_STOP`; stop redis, `docker cp` the RDB, start; extract storage, chown/chmod; compare pre-start summaries (table count, row total, role count, row-hash, Redis DBSIZE and queue lengths, storage count/bytes) - any mismatch aborts; run backend-init (waits for exit 0); start backend, frontend, worker, processing-worker, beat.
- Verify: requires `TARGET_PRESTART_SUMMARY_MATCH=1`; container health; live DB/storage summary re-compare; nginx/certbot if DNS points at target, then HTTPS GETs of `/` and `/api/csrf/`; cleanup remote bundle; local bundle deleted only when KEEP_STAGING=0. On any failure after freeze, an EXIT trap restarts the source stack. After success the owner must manually repoint DEPLOY_IP and decommission source.

### 2.7 Resource configuration values
Documented defaults (production doc): BACKEND 700m/1.0 CPU; WORKER 600m/0.5; PROCESSING_WORKER 900m/2.0; REDIS 320m/0.5 with `REDIS_MAXMEMORY=256mb`; GUNICORN_WORKERS 2, TIMEOUT 120, MAX_REQUESTS 500 (+jitter 50); CELERY_WORKER_CONCURRENCY 2; CELERY_PROCESSING_CONCURRENCY 1. Sizing profiles: min 2 CPU/4 GB (backend 600m, worker 400m, processing 1200m, 1 concurrency), recommended 4/8 (1g, 600m, 2500m, gunicorn 3), high 8/16 (2g, 1g, 6g, gunicorn 4, processing concurrency 2). Rules: gunicorn workers = 2N+1, backend mem >= workers x 150m; processing mem ~60% of host if large books; `GUNICORN_TIMEOUT` 360 if 504s. Each processing child ~400 MB (`worker_max_memory_per_child`), large books (2,000-2,300+ topics) need 2-4 GB per scrape. Disk page cache of fetched pages at `<RUNTIME_STORAGE_DIR>/processing/scrape_cache/`, deleted after a successful build, lets an OOM-killed scrape resume. Old profile: 3.72 GB host, steady RSS <= 1.6 GB, CPU 1-5%. No explicit Celery `time_limit` for tasks. Host nginx: `client_max_body_size 64m`, `proxy_read_timeout 300s`.

### 2.8 Source-site auth cookie procedure
Purpose: LearnDash paginates the lesson (TOC) list; pages 2+ return only to an authenticated request. Cloudflare blocks every automated login, so login is never scripted. Procedure: (1) log in to the source site in Firefox with "Remember Me" (cookie lasts about 1 year); (2) `bash local/scripts/save-source-site-auth.sh` (pip-installs `browser-cookie3` if missing, reads Firefox's `wordpress_logged_in_*` cookie, falls back to manual paste of name/value from DevTools; env `SOURCE_SITE_SKIP_BROWSER_READ=1` forces paste); (3) writes a Playwright-style storage-state JSON `{cookies:[...],origins:[]}` to `app/backend/storage/source_site_auth.json` (httpOnly, secure, Lax, path /); (4) local containers see it through the bind mount; deployed hosts get it via `sync_source_site_auth_file()` (scp) during deploy or manual scp. The backend re-reads the file per scrape session (no restart). Expiry symptom: error "Sign-in required: the source table of contents spans multiple pages ... only N of M TOC pages could be retrieved. Update the source site auth cookie and regenerate this book." Path = `SOURCE_SITE_AUTH_STATE_PATH` else `<RUNTIME_STORAGE_DIR>/source_site_auth.json`. `SOURCE_SITE_EMAIL`/`PASSWORD` env keys exist but docs say login is never automated.

### 2.9 Backups
None. No scheduled `pg_dump`, no volume snapshot, no storage (books/media) backup, no offsite copy, no restore drill. The only dump capability is the one-shot migration bundle, which also contains the full `.app.env` (secrets) in plaintext in `migration/runtime/` and is KEPT locally by default. Redis is a plain `redis-server` with default persistence. The rebuild must define backup/restore itself.

### 2.10 TLS and edge
Host nginx (installed from nginx.org apt repo, pinned version, `apt-mark hold`) + certbot (webroot `/var/www/certbot`, `certonly --non-interactive --agree-tos --no-eff-email -m <email>`). Two-pass config: HTTP bootstrap server for ACME, then HTTPS: 80 -> 301 to https, 443 ssl, TLSv1.2/1.3, session cache 10m/1d, `ssl_prefer_server_ciphers off`; NO HSTS, OCSP stapling or security headers. Routing: `/api/` and `/admin/` -> backend (127.0.0.1:BACKEND_PORT), `/static/` alias to host `storage/staticfiles` (7 d cache), `/media/` alias to host `storage/media` (1 h cache, no auth), `/` -> frontend container. Directory traversal permissions are loosened (`chmod o+x` on parents of the app dir, `o+rX` on static/media). Renewal: `certbot.timer` if present, else `/etc/cron.d/certbot-renew` every 12 h; deploy hook reloads nginx. Backend trusts `X-Forwarded-Proto/Host`. Single domain, single certificate, no wildcard.

## 5. Doc vs code contradictions

1. Resource limits: `production-resource-configuration.md` says `deploy.resources.limits.memory` "is already applied in deploy/compose/docker-compose.yml" and lists CPU limits and `REDIS_MAXMEMORY`. The actual `deploy/compose/docker-compose.yml` has NO `deploy:` blocks, no cpus, no mem limits, and Redis runs bare `redis-server` with no `--maxmemory`. `PROCESSING_WORKER_MEM_LIMIT` named in deployment.md is therefore not enforced. The "mem_limit ignored" fix was documented but never landed in the file (or was lost).
2. Services: deployment/local docs and release note list 7 services; compose also runs `engine` (`run_engine`), undocumented everywhere in docs. Migration health checks and restart lists, the log viewer and `dev.sh logs` groups omit `engine` (migration restore never starts it on the target).
3. Worker roles: release note says the processing worker is for "catalog sync, incomplete detection, automation tasks" and the general worker for "book creation pipeline, EPUB generation, Kindle"; the resource docs say processing-worker is the book-scraping queue and the general worker is email/catalog tasks.
4. Migration: doc says Snapshot "restarts the source stack after the dump" and that `postgres, redis, worker, processing-worker` remain running during the dump; code stops workers after drain, and in a `full` run restarts the source only in `finalize_success` (after restore + verify), so the source stays frozen throughout. Doc says `pg_dumpall`; code uses `pg_dumpall --globals-only` plus `pg_dump` of the one DB. Doc says "local bundle deleted on success by default"; code defaults `KEEP_STAGING=1`. Doc table lists `TARGET_USER` twice. Doc/usage name AWS->DigitalOcean specifically.
5. Local dev doc says backend uses "Django autoreload"; compose runs `runserver --noreload` and relies on sync only (backend does not restart). Doc says "detects your Mac's active LAN IP"; the helper has Linux fallback via `ifconfig` only. Local backend healthcheck uses `/api/health/` whereas every other environment uses `/api/csrf/`.
6. Local-development doc lists worker/processing-worker/beat but not `engine`, nor the `--pool=solo` worker flags; `dev.sh logs backend` group (service_group_for_logs) includes processing-worker while log-viewing.md says only backend, worker, beat.
7. Processing page count: reference/audit state "four consolidated routes" while the same audit and the release note add `/multipage-toc` and `/reprocessing` (six routes); reference still documents an "old page inventory" and the old six-page model.
8. Deployment doc step list says "syncs the target branch" then "syncs the local workspace"; the real flow is `git reset --hard` followed by overlaying uncommitted local files (so deployed code may differ from the branch). Doc says default deploy "recreates frontend and backend stack"; the script does `down --remove-orphans` then recreates everything (downtime).
9. Nginx versions: README says Nginx 1.27 (container image), host nginx default is pinned 1.29.4. Release note says "Redis 7 Celery result backend" and compose agrees; README tech table says Celery 5.6.
10. Release note says CSRF/secure cookie flags "Secure, SameSite=Lax, HttpOnly"; local/local-production compose set Secure=0 and the deploy default for `DJANGO_ALLOWED_HOSTS` includes `nginx`, a host that does not exist in compose.
11. `processing-pages-reference.md` "Validated" results quote test counts (10, 9, 8, 14 passed) that cannot be verified here; the live-test matrix forbids mocking, while the reference's "mocked browser edge-case sweep" (14 specs) uses mocks.
12. ebangla-auth-cookie doc title/filename names the real site while content is sanitised.
13. `local/scripts/clear_docker.sh` and `dockerctl` are not referenced by any doc except local-production's prerequisite hint.
