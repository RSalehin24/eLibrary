## B. Data migrations and DB-level logic (behaviour)
- **M44 catalog/0004** (97 lines): `RunPython` backfill of display name (NFKC + whitespace collapse), `normalized_*` (lowercase, keep only Unicode letters L/number N/mark M, spaces) and `slug` (unicode slugify, collision suffix -2,-3 by per-row existence queries) for Contributor, Series, Category, Book. Reverse is noop. N+1 queries over all rows. Reveals the original ASCII-only slug/normalisation bug for Bengali text (0003 added `normalized_*` first, 0004 repaired data one day later).
- **M45 catalog/0006** (176 lines) and **0007** (175 lines): add `catalog_code` (10 chars from a 32-symbol alphabet without 0/1/I/O, 50 bits) for Category (16-bit sequence), Contributor, Book. Book code packs tag(2) + category seq(16) + writer seq(16) + per-pair book seq(12) + check(~4); then an affine scramble `(payload*mult+offset) mod 32^10` obfuscates it. Backfill ordered by created_at,name,id. 0007 re-runs the identical algorithm (the constant block and builder functions are byte-identical to 0006; it also issues Postgres `ALTER COLUMN catalog_code TYPE varchar(10)` before/after) "rehash" - evidence of a previous length/format change that was done in place. 0014 repeats the whole scheme for Series with tag 0 and its own offset. Limits: 65 535 categories/writers, 4 095 books per (category, writer) pair; raises ValueError beyond. The code is derivable from sequence numbers (no secret), so it is obfuscation not security; and it depends on `created_at` ordering at migration time, so codes are not stable across re-imports. The same ~60-line algorithm is copy-pasted 3 times because migrations cannot import app code safely.
- **M46 catalog/0012**: creates UserBook and backfills one row per distinct (submitter, linked_book) pair from BookSubmission (iterator, bulk_create ignore_conflicts), preserving created_at/updated_at. Meaning: "my books" was originally derived from submissions, then materialised.
- **M47 catalog/0019**: before `unique_together=('book',)` on BookSource, deletes duplicate BookSource rows per book keeping the primary / newest (irreversible deletion; reverse is noop). Destroys alternate-source data without archiving.
- **M48 access/0009**: renames scope value `preview:read_once` to `preview:html` for existing grants (reversible) while changing choices and adding `send:kindle`. 0010 adds a new `read:once` and re-labels; 0012 adds `physical_books:view` only as choices (no data). Max length 32 stays. Scope strings are stored as free text, so every new permission is a migration that only changes `choices` (no DB effect) - churn without value.
- **M49 processing/0003** (366 lines): creates the two UI-state tables and seeds them: renames sync state `default` to `catalog`, creates `catalog` and `incomplete` states, creates automation settings per kind (weekly 03:00, disabled) and normalises unsaved ones, computes counts from BookCreationRequest/BookRecord (incomplete detection by `category` containing keywords incomplete/unfinished/Bengali "oshompurno"), builds seven projection payloads and zeroed domain versions for 18 domains (catalog-*, create-*, on-hold-*, incomplete-*). Hard-codes camelCase JSON shapes of the Angular/JS UI in a migration.
- **M50 processing/0004** (150 lines, `RunSQL`, Postgres/plpgsql only, no vendor guard, reversible via DROP): function `processing_sync_book_record_state(record_id)` sets `BookRecord.book_creation_state` to the state of the latest BookCreationRequest (ordered updated_at desc, created_at desc, id asc), else `created` if linked_book set, else keep/clamp to the allowed list. Trigger AFTER INSERT/UPDATE OF state,book_record_id,updated_at,created_at/DELETE on request rows, plus BEFORE INSERT/UPDATE OF book_creation_state,linked_book_id trigger on BookRecord that overwrites the incoming value with the derived one (so application writes to `book_creation_state` are silently ignored when requests exist). Cause: the denormalised state drifted from requests; fix was put in the DB. The sync function also updates `updated_at = NOW()`, bypassing Django auto_now semantics. Migration cannot run on SQLite (tests need Postgres).

## C. Dependency graph and churn analysis
- Cross-app graph: catalog.0002 -> ingestion.0001 -> catalog.0001; access.0002 -> catalog.0001 + ingestion.0001; access.0005/0007 -> catalog.0013; access.0011 -> catalog.0019; catalog.0012/0013 -> ingestion.0008; processing.0001 -> catalog.0011; processing.0002 -> ingestion.0008. Circular model coupling (catalog.GeneratedAsset -> ingestion.ProcessingJob while ingestion.BookSubmission -> catalog.Book) forced split `0001_initial` + `0002_initial` in catalog, access and (via FK) ingestion. For the rebuild this means catalog and ingestion are not separable bounded contexts as modelled.
- **M51 Timeline**: Mar 21 2026 initial schema (all six apps, 09:42) and SavedFilter (10:40); same day normalised_* + unique constraint (10:12) then removed Mar 27 (0011) once real data showed titles collide across sources/editions; Mar 22 TOTP flag, profile image, categories/contributors in grants, canonical_submission, curation runs; Mar 22-23 automation settings then frequency; URL fields widened to 1000 in catalog/0005 and ingestion/0004 (Bengali percent-encoded URLs overflow 200 chars default); May 24 highlights (+kind quote); May 29 asset path length; June 4-6 permission scopes churn (0008, 0009, 0010 in 3 days), BookSource single-source, opening records, Kindle send; June 30 rebrand of defaults from the named source site to generic `source_site*` and a Django 4.2.30 header on 0023 (generated with a downgraded Django vs 5.2.12 in all earlier files; migration generated by an older environment: version drift). Jul 6 physical_books permission.
- **M52 Design churn signals**: (1) `last_kindle_sent_at` on Book added (0020) and dropped (0022) in favour of per-user `UserBookKindleSend`, whose pk lacked a default until 0023 (bug: `id` UUID without default, 0021:17). (2) Book-source model went from many-sources-per-book (is_primary, source_type) to exactly one (0019). (3) Permission scope names renamed in place (preview:read_once -> preview:html) then `read:once` re-added with a different meaning. (4) Two normalisation systems: `normalized_*` columns (catalog) vs string columns on `BookRecord` (processing). (5) Two pipelines for book creation: ingestion.BookSubmission/ProcessingJob/ProcessingLog and processing.BookRecord/BookCreationRequest, linked via OneToOne submission (processing/0002:37-47); both track duplicates (DuplicateReview vs duplicate_of_record/request) and queue/cancel state. (6) Admin UI state persisted as DB projections and domain version counters (M40, M41), a poll/ETag cache living in Postgres, plus triggers to keep a derived column honest. (7) Singleton tables via `singleton_key` / `kind` (M33, M35, M38, M39) instead of settings; three different singleton idioms. (8) Index added late for hot filters (catalog/0018, ingestion/0009) - performance issues discovered in production. (9) Grants allow book/category/contributor targets but access/0002 ordering uses `book__title` etc. (join-heavy default orderings on many models, e.g. PermissionGrant ordering by user__email, scope, book__title, category__name, contributor__name; Bookmark ordering by book__title), a latent performance hazard.

## D. Issues (rebuild must not repeat)
- **M53** Full book content stored in DB columns (`main_content_html`, `book_info_html`, `dedication_html`, `toc`, `content_items`, `CuratedSection.html`) plus file assets: duplicate storage of content; row bloat.
- **M54** Free-text/choices-only enums: DB accepts any scope/state string; no CHECK constraints; choices changes churn migrations.
- **M55** `PermissionGrant` has no uniqueness and no target-validity constraint; duplicates and nonsense rows possible.
- **M56** `AuditLog.target_id` is a char string with no FK; no immutability guarantee; `updated_at` exists on an append-only log.
- **M57** Identifier collisions: `BookRecord.id` string generated in app code; BookRecord.url unique but Book has no unique natural key except BookSource.normalized_source_url.
- **M58** Data-destroying migration (0019) and noop reverses on all data migrations except access/0009.
- **M59** Postgres-specific migration code with no test alternative (processing/0004, catalog/0007/0014).
- **M60** `UserBookKindleSend` and `BookOpeningRecord` carry only timestamps; no send status, target address, error or count, so Kindle delivery history/failure cannot be shown.
- **M61** `kindle_emails` stored as JSON array on user with no validation at DB level (verification of ownership of the address is not representable).
- **M62** `ReadingSession.last_opened_at` is auto_now, so any progress save changes "last opened"; duplicate concept with BookOpeningRecord.
