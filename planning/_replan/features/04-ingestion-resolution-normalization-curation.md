## 5. Bugs, dead code, duplication, surprises

1. `get_with_host_fallback` defined twice with identical logic (resolution.py:36-69 and resolution_support_network.py:241-268). `resolution.py` also re-wraps `resolve_host_with_dns_fallback` / `get_via_direct_ip_https` in trivial lambdas; `TitleResolver` calls the local copy (so tests that patch the support module miss it). `is_name_resolution_failure` is imported from `resolution_support` though it is defined in `resolution_support_hosts`.
2. DoH lookup uses `verify=False` against `https://1.1.1.1` (TLS verification disabled) — resolution_support_network.py:130. A rebuild must not copy this. The DNS and direct-IP fallback exists only because the host sometimes fails name resolution; rebuild should drop it or make it opt-in config.
3. Name-resolution detection is string matching on exception text (`"name resolution"` / `"gaierror"`), locale/library fragile.
4. `score_candidate_fields`: if the catalog entry title normalises to empty, `normalized_title in normalized_query` is `"" in ...` -> True and the entry scores 0.78; also any 1-2 character title is a substring match for many queries. `ambiguous` result with a lone 0.78 candidate returns no URL, so a single close match is never auto-resolved unless exactly 1.0 (or the two top are not both 1.0). An `exact_match` is also awarded when two candidates tie at 1.0? No: tie -> `ambiguous`.
5. `texts_are_similar` and `normalize_text` live in `apps.ingestion.pipeline.scraper_support.text` (not in my scope) — the 0.88 tier threshold is defined there.
6. `refresh_catalog` uses `update_or_create(defaults=entry)` which overwrites `raw_data` (loses book_page metadata); the later `upsert_source_catalog_entry` merges. It also returns only created entries, not updated ones, and runs one DB query per entry (N+1). `last_seen_at` is not set explicitly here (presumably auto field on save) — unverifiable from these files.
7. `resolve()` runs a full unbounded archive crawl (`max_pages=None`) per letter bucket synchronously when no candidates exist, inside the request path; `enrich_candidates_with_source_metadata` does up to 3 live HTTP fetches and swallows every exception silently.
8. `trailing_looks_like_contributor_phrase` suffix check uses plain substring on the normalised string, so "vol", "part", "edition", "series" also reject names containing those letters ("Volkov", "Parthasarathi"). Same substring semantics in `looks_like_address_fragment` (`ADDRESS_FRAGMENT_WORDS` such as "row", "road", "ঢাকা" are substring-matched: "Crowley", "Broad", "Arrow" are rejected as contributor names).
9. `MIDSTRING_ROLE_LABELS` is built from role aliases ending in " by" but no such alias exists in the table, so it is always empty and the related branches in `metadata_label_matches` behave as unconditional rejects; dead intent.
10. Duplicated entries in constant lists (look like copy/paste normalisation artifacts, visually identical but possibly different Unicode forms): `NON_CONTRIBUTOR_TITLE_SUFFIXES` "অধ্যায়" twice, `ROLE_PATTERNS` "সম্পাদনায়" twice, `NON_PERSON_TITLE_WORDS` "অধ্যায়" twice, `ADDRESS_FRAGMENT_WORDS` "সড়ক" twice, `PUBLISHER_NON_NAME_WORDS` "বইয়ের" twice, page_count pattern twice, edition patterns "দ্বিতীয়/তৃতীয় সংস্করণ" twice, `BODY_SECTION_PATTERNS` "অধ্যায়" twice, supplementary "নমুনা/প্রিভিউ অধ্যায়" twice. Likely the second of each pair is a different Unicode composition (e.g. precomposed য় vs য + nukta); the rebuild must normalise Bengali Unicode (NFC with nukta composition) at the single entry point, otherwise matches silently fail.
11. `CANONICAL_BOOK_INFO_KEY_ORDER` lists `original_title` twice and `ContributorRole.COMPILER` (unreachable because `canonical_role` folds compiler to editor). `ContributorRole.OTHER` label exists but no code path produces it.
12. `format_book_info_html_ordered` mutates the module-level label dicts (`labels.setdefault(key_slug, label)` where `labels` is `BOOK_INFO_KEY_LABELS_BN/EN` itself): unknown labels leak between books/requests for the process lifetime. It also silently discards unparsed lines ("raw_lines" are collected, never emitted).
13. `extract_main_content_segments` danda-split writes `f"<{block.name}>{part}</{block.name}>"` without HTML-escaping (HTML injection of scraped text into book_info; other emitters use `escape`). Same function rejoins non-meta sentences with "। " even if the original separator differed.
14. `_generate_residual_heading` is dead code; `skipped_deleted` summary counter never incremented; `OVERVIEW_CURATION_STATUSES` contains `"requeued"` which is never produced; `status_counts` skeleton lacks "queued"; `quality_gate.book_quality_gate` is not called from any file I read; `resolution_support.get_source_site_domain`, `source_catalog_entry_snapshots`, `next_catalog_automation_run_at` (alias of due_at) and `validate_source_url` alias are unused wrappers here. `extract_leading_front_matter_html`'s other two return values discarded.
15. The `exec()`-composition facades hide dependencies (module files have no imports, rely on earlier files' globals; e.g. `catalog_automation_runs.py` uses `timezone`, `logger`, `CatalogCurationRun` from the sibling file). Names such as `ASCII_TO_BANGLA_DIGITS` are used (line 157) before they are defined (line 548) in the same file; works only because calls happen after import.
16. Curation run cancellation is cooperative with a DB round-trip per entry (`refresh_from_db` for every catalog entry). Run lock ("busy") only guards the scheduled path; manual `create_catalog_curation_run` can overlap other runs. `run_due_catalog_automation` has a race (check-then-create without a lock) and `already_ran` logic relies on comparing created_at with settings.updated_at, so any settings edit re-arms "today_slot" and can trigger a second run the same day if `daily_run_time` already passed (due = today_slot is in the past, now >= due).
17. `next_catalog_automation_due_at` computes the next date from the last run's creation DATE (not scheduled slot), so schedule drifts by whenever the previous run was created (long queue delay shifts later runs); weekly/etc. use calendar dates in the current timezone.
18. Inline fallback: on broker failure the web request itself runs the whole refresh/curation run synchronously (could take hours, no timeout). Task-id ownership guards in `process_source_catalog_refresh` exist for refresh, but `process_catalog_curation_run` has no stale-task guard.
19. `CatalogAutomationSettings.refresh_max_pages` / run `refresh_max_pages` are stored but `process_catalog_curation_run` calls `refresh_catalog_parallel()` with no argument, so the max-pages setting is never applied to runs or to `process_source_catalog_refresh` either. (Behaviour of `refresh_catalog_parallel`, in `apps.processing.services`, not verified.)
20. `activity.py` imports from `submissions` (partner file) and `curation` (exec facade); not circular only because of import order.
21. Failed-entry classification treats submission statuses `needs_review` and `duplicate` as "failed", so duplicates are retried (after the 6 h cooldown) and a `duplicate` entry can be re-created repeatedly by scheduled runs.
22. Legacy host normalisation forces scheme https and rewrites any allowed host to `SOURCE_SITE_HOST`; query strings are dropped, so URLs differing only by query collapse together.
