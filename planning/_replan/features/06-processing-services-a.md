## 4. UI-domain invalidation mechanism (in detail)

Files: ui_domain_versions.py, ui_projection_queries.py, service_imports_and_constants.py (constants), state_serializers.py (`processing_request_card_for_state`, `processing_overview_card_for_state`, snapshots), processing_card_payloads.py, processing_state_queries.py. SSE itself is NOT in my slice: nothing here opens a stream. What exists is the server-side data needed by an SSE/poll endpoint: monotonically increasing per-domain integer versions plus cached projections plus `processing_ui_versions_diff(previous_versions, domains=None)` returning `(changed_versions, current_versions)` for domains whose version is greater than the client's. The SSE view/consumer lives elsewhere (views/tasks, not read) - flag for the other agent.

Components:
1. Domains: the 20 `PROCESSING_CARD_KEYS` (see F123 + shared cards `catalog-overview, catalog-sync, catalog-automation, create-overview, on-hold-overview, incomplete-overview, incomplete-automation`). `PROCESSING_PAGE_DOMAINS` groups them by page: catalog, create, on-hold, incomplete, multipage, empty-chapters. Rows in table `ProcessingUiDomainVersion(domain, version, updated_at)`.
2. Projections: `ProcessingUiProjection(key, payload JSON, updated_at)` rows exist only for the 7 shared cards (`PROCESSING_SHARED_CARD_KEYS`). Table cards (lists) are NOT projected; they are queried on demand and stamped with the domain version.
3. Dependency map `PROCESSING_SHARED_PROJECTION_DEPENDENCIES`: bumping domain D rebuilds projection keys in `deps[D]`. Notably `catalog-sync` rebuilds `catalog-sync` AND `catalog-automation` (because the automation payload embeds the sync payload); every other shared domain rebuilds only itself. `incomplete-automation` holds both the incomplete sync and the incomplete automation settings. Non-shared (table) domains have no projection.
4. Publish: `publish_processing_ui_domains(domains)` filters to known keys (silently drops unknown), sorts, and registers `transaction.on_commit(commit)`. `commit()` (a) rebuilds the dependent projections (`rebuild_processing_ui_state`: ensures rows exist via `bulk_create(ignore_conflicts)`, recomputes payloads with full summary queries, `update_or_create` per key); then (b) in `transaction.atomic` bumps each domain: `bulk_create(version=0, ignore_conflicts)` to guarantee rows, `select_for_update` ordered by domain (stable lock order), `version += 1`, save. Note the order: projection rebuilt first, version bumped after, so a client that sees version N+1 always finds a projection at least as fresh. Outside a transaction `on_commit` runs immediately.
5. Version collector: `collect_processing_ui_version_updates()` context manager sets a `ContextVar` dict. While active, `publish_processing_ui_domains` precomputes (`_plan_processing_ui_versions`) expected next versions = `max(current DB version, collected) + 1` and, after commit, merges actual versions (`_merge_processing_ui_versions` keeps the max). The caller (a view, not in slice) can therefore return the new versions to the acting client in the HTTP response so the client can ignore its own SSE echo. Nested contexts reuse the outer collector.
6. Which events bump which domains:
   - Request transition (`processing_domains_for_request_change(before, after, record)`): always `catalog-overview`, `catalog-records`, `multipage-records`; plus the request card for the before and after state (`create-requests|create-queue|create-processing|create-created|on-hold-paused|failed|duplicate|deleted`); plus overview for before/after group (`create-overview` for initial/queued/processing/created, `on-hold-overview` for paused/failed/duplicate/deleted); if the record is incomplete -> `incomplete-overview`, `incomplete-records`; if record was incomplete and resolved -> `incomplete-overview`, `incomplete-completed`.
   - Record change (`processing_domains_for_record_change(before_snapshot, after_snapshot, current_request_state)`): `catalog-overview`, `catalog-records`; the card of the current request state if given; incomplete overview/records if either snapshot is incomplete; incomplete overview/completed if either is resolved. Snapshots hold `id, category, was_incomplete, resolved_from_incomplete, book_creation_state, linked_book_id, is_duplicate, duplicate_of_record_id` (request snapshot also exists but is unused in this slice).
   - Sync state save (`save_sync_state` -> `processing_domains_for_sync_state`): `incomplete-automation` for key `incomplete`, otherwise `catalog-sync`.
   - Automation settings change (`processing_domains_for_automation`): `incomplete-automation` or `catalog-automation`.
   - Automation-origin request creation adds `catalog-automation` and `create-overview`.
   - Reset: all 20 domains.
   - Never bumped here: `empty-chapters-records` (depends on `linked_book.empty_chapters_count`, written elsewhere) - will only change if another module publishes it.
7. Consumption: `processing_state_payload` returns `versions` map (all domains) and shared cards from projection rows (default payload if row missing, `default_processing_shared_projection_payload`). `processing_table_payload` and `processing_card_payload` stamp `version`. `processing_ui_versions_map(domains)` defaults missing rows to 0.
8. Atomicity/consistency characteristics: version bump is per-commit (batches publish once per page/batch in the sync loops); bump and projection rebuild are not in the same transaction as the data change (on_commit), so a crash between commit and the hook loses the notification (no outbox); concurrent publishes serialize on the version rows.

## 6. Bugs, dead code, duplication, surprises

1. [High] Empty incomplete candidate list resolves EVERYTHING. `incomplete_automation_pages()` only includes records that already have `will_resolve_to_category`. If none do, remote_pages is `[[]]`; `advance_incomplete_sync_once` then takes the `not page` branch and calls `stale_incomplete_record_ids(remote_pages)`; `incomplete_remote_urls` yields an empty set (pages of ids are not dict pages -> `catalog_remote_pages` returns `[]`), so every unresolved incomplete record is "stale" and gets resolved to category "Uncategorized"/CREATED without any Book (incomplete_resolution.py:86-97; automation_advancement.py:189-203; sync_runner.py:11-16).
2. [High] "Resolved" incomplete means "disappeared from the incomplete archive", and `resolve_incomplete_records` marks request and record CREATED although no Book was built (incomplete_resolution.py:3-53).
3. [High] Catalog re-sync overwrites record fields including `resolved_from_incomplete` (False from the payload), `category`, `linked_book`, and `book_creation_state`; payload built from SourceCatalogEntry never carries `resolvedFromIncomplete`, so a later catalog sync un-resolves resolved incomplete books. Also `book_creation_state` default overwrite makes any record with a request (e.g. FAILED) count as "updated" every sync until `sync_record_state` restores it (catalog_record_sync.py:27-46,81-94).
4. [High] `refresh_catalog_parallel` has no max page and swallows all exceptions: with the source down every worker loops forever (always `continue`), only an empty page stops it; no pause check while running; counters reported only at the end; no logging (catalog_record_sync.py:240-264).
5. [Med] `apply_new_edition_action`: group wiring depends on a `request.submission` relation which the current pipeline does not create or read (`persist_*` called with `None` submission), so "new edition" = "new" plus an orphan BookGroup created for the existing book (request_action_dispatch.py:30-47).
6.
