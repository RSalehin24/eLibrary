## 3. Sync runner in detail

Scopes (singleton rows of `ProcessingSyncState`, `singleton_key`): `catalog` (PROCESSING_SYNC_KEY_CATALOG) and `incomplete` (PROCESSING_SYNC_KEY_INCOMPLETE). Statuses (ProcessingSyncStatus): IDLE, SYNCING, PAUSING, PAUSED. SYNC_ACTIVE_STATUSES = {SYNCING, PAUSING}. Run modes: `manual`, `catalog_automation`, `incomplete_automation`. Trigger sources: `button`, `scheduler`.

Phases (catalog scope only): `sync` and `request_creation`; phase statuses: not_started, running, pausing, paused, completed. Progress is stored in `state.progress` JSON as phases dict built by `build_catalog_progress_payload` (other file). Per phase: status, owner (run mode), triggerSource, checkpoint (`page-{n}` for sync, `request-{lastRecordId or processedCount}` for request creation), savedAt, savedData {runMode, triggerSource, fetchedCount, nextPageIndex, sessionId, checkpointToken, liveFetch}, requestCreation {baseCheckpointToken, lastRecordId, processedCount, createdCount, unsupportedCount}, baseSyncCheckpointToken. Incomplete scope uses the flat `build_sync_progress` payload: runMode, triggerSource, phase "sync", checkpoint `page-{n}`, savedData {runMode, triggerSource, fetchedCount, nextPageIndex, [sessionId, checkpointToken], [liveFetch]}, [savedAt].

Checkpoint token: `catalog_sync_checkpoint_token(session_id, next_page_index, fetched_count, live_fetch)` (body in a file before `r`; key prefix constant `processing:sync-checkpoint` = PROCESSING_SYNC_CHECKPOINT_KEY_PREFIX, used for the Redis mirror, imports `Redis`, `RedisError`). The Redis mirror implementation is NOT in my files; I could only see the prefix and imports.

Dispatcher `run_processing_sync(key, task_id)`: load state (raises DoesNotExist if row absent); ignore if a different task id owns it (`task_id and state.task_id and state.task_id != task_id`); ignore if not SYNCING/PAUSING. Then:
1. run mode incomplete_automation -> `advance_incomplete_sync_once` (one page/step).
2. catalog scope phase == request_creation -> `advance_catalog_request_creation_once`.
3. not live fetch -> `advance_catalog_sync_once(state, run_mode)` (page of saved `remote_pages`, one step).
4. live fetch -> `run_processing_sync_until_blocked`.

`run_processing_sync_until_blocked`: same guards. Incomplete: loop refresh_from_db / guard / advance_incomplete_sync_once until status leaves active. Non-live catalog: loop with `advance_catalog_processing_once(state, run_mode)` (other file) until non-active. Live catalog: single call `refresh_catalog_parallel()` returning `{total, appended_count, updated_count}`; refresh state; re-check ownership; add counts; read `persisted_sync_status`. If PAUSING -> status PAUSED, sync phase "paused" with savedAt, message "Sync progress saved. Catalog now has N book records.", update automation run status, return. If not SYNCING -> return DB row. If run_mode is catalog_automation -> `begin_catalog_request_creation` (switch to phase request_creation; note it only sets state, then falls through to `finalize_catalog_sync`; see surprise). Else `finalize_catalog_sync`. Exceptions -> `fail_sync` (status IDLE, last_error, message "{label} failed: {err}"). A live sync cannot pause mid-fetch: pause only takes effect after the whole parallel refresh finishes.

Incomplete sync step `advance_incomplete_sync_once`: live -> `advance_live_incomplete_sync_once` (other file) with exception -> fail_sync. Non-live: `remote_pages` is a list of pages; page empty/out-of-range -> resolve incomplete records not in remote list (`stale_incomplete_record_ids(remote_pages)`) and complete. A page of non-dicts (list of ids) -> `resolve_incomplete_records(page)`, counts fetched/updated. A page of dicts -> `upsert_remote_records(page)` skipped/appended counts. After each page: persisted status PAUSING -> PAUSED with progress `build_sync_progress` saved_at, message "Saved progress for N record(s) before pausing."; status not SYNCING (e.g. stopped) -> return DB row; no next page -> resolve stale incomplete records and `complete_incomplete_automation`; else update progress and message "Processed N incomplete record(s) so far.". Pause is cooperative: checked via `persisted_sync_status` DB read after each page.

Resume (`resume_sync(sync_key, run_mode=None)`):
- run_mode defaults to the state's run mode.
- run_mode incomplete_automation: `remote_pages` reset to [] if live else `incomplete_sync_remote_pages()`; always page 0 (restart from beginning; fetched_count preserved), message "Restarting incomplete catalog sync from the beginning." (so incomplete "resume" is really a restart).
- Catalog scope: read saved data and request_creation from phases. `sync_can_resume` = status PAUSED and sync phase status paused. If run_mode == catalog_automation and `catalog_request_creation_can_resume(state)`: set SYNCING, page_index/fetched_count from saved sync phase, progress request-creation phase "running", clear task_id/queue_name, message "Resuming automated request creation from saved progress.", save, update automation status, then dispatch (`dispatch_sync_task(state, force=True)` if worker mode, or run inline until blocked) and return. Else if `sync_can_resume`: message by `catalog_sync_resume_message`, page from `nextPageIndex`, fetched from `fetchedCount`. Else restart from 0 (counts zero, saved_data empty, request_creation phase kept only if it was paused), messages "Restarting automated catalog sync from the beginning." / "Restarting catalog sync from the beginning.".
- Other scopes fall into last else branch: page 0, message "Restarting automated catalog sync from the beginning." for catalog_automation else "Reconciling saved records from the beginning." (dead for current two scopes except incomplete w/ other run mode).
- Then status SYNCING; progress rebuilt (catalog: `build_catalog_sync_progress` with sessionId reused or new uuid4, phase running; other: `build_sync_progress`); page_index, fetched_count set; counts skipped/updated/appended zeroed only when restarting catalog from 0; task_id/queue_name cleared; save with fields incl. `remote_pages`; update automation status; dispatch Celery sync task `force=True` if `should_enqueue_processing_sync_work()` else run inline if `should_run_processing_jobs_inline()`; else nothing (manual stepping via `advance_sync_once`).

Pause/ownership of runtime between manual and automation:
- `sync_run_mode(state)` is derived from the state (other file). `sync_owner_conflicts(state, run_mode)`: when state is SYNCING/PAUSING, conflict iff its run mode differs from the requested one; when PAUSED, conflict iff run modes differ EXCEPT for the catalog scope where both the paused mode and the requested mode are "catalog shared runtime" (`catalog_shared_runtime`, other file; presumably manual and catalog_automation share the catalog runtime so either can resume the other's paused sync); otherwise (IDLE) no conflict. The incomplete scope has a single owner (incomplete_automation).
- `active_sync_scope()`: incomplete scope takes precedence over catalog when both are SYNCING/PAUSING/PAUSED (so pause/stop buttons with no key target incomplete first).
- Automation completion of catalog sync (live) hands over to request-creation phase under the same SYNCING status and same state row; manual catalog sync does not create requests.
- `update_automation_run_status(run_mode, message, last_run_at=None)` only mirrors messages for automation run modes (manual returns None); creates automation settings row if pk None; publishes `catalog-automation` / `incomplete-automation` domain — sync_status_messages.py:237-255.

Redis mirror: not found in files r..z beyond imports `Redis`, `RedisError` and constant `PROCESSING_SYNC_CHECKPOINT_KEY_PREFIX="processing:sync-checkpoint"` (service_imports_and_constants.py:38-39,155). `save_sync_state` is in another file. Worker availability cache: `PROCESSING_WORKER_AVAILABILITY` dict {checked_at 0.0, available None}, TTL `PROCESSING_WORKER_CACHE_SECONDS`=2.

## 5. Request actions summary (rules)

| action | state result | flags | side effects |
|---|---|---|---|
| start (queue) | INITIAL -> QUEUED -> PROCESSING | none | queue_processing_request; URL must pass `can_process_record_url` else FAILED "Only source site book URLs are allowed" |
| stop/pause | other agent file | | when PAUSED the worker saves checkpoint at next safe point (`source-metadata` or `scraped-content` checkpoint constants) |
| resume | other agent file | sets `is_resumed` | pipeline uses saved scraped data only when `is_resumed` and checkpoint == scraped content checkpoint |
| retry / force_generate / delete | other agent file | | force flag consumed in `_persist_processing_book`; DELETED request soft-deletes the book on finalize |
| recreate (`create_again`/`recreate`) | INITIAL | force False, progress None, error "", duplicate_confirmed False; record dup flags cleared; linked_book and is_confirmed_not_duplicate kept | queue |
| new | INITIAL | is_confirmed_not_duplicate True; all links cleared | queue |
| new_edition | INITIAL (via new) | writes target_book_group_id into submission.raw_payload; BookGroup created lazily | queue |
| confirm_duplicate | DUPLICATE | duplicate_confirmed True | links to target request/record; no queueing |
| bulk | `apply_request_action` loops ids ordered by created_at; unknown action ignored; `delete_book` flag only used by delete |
Duplicate decision machinery: automatic duplicate detection yields DUPLICATE with links (`_mark_request_duplicate`), the user then picks `new`/`new_edition` (process anyway) or `confirm_duplicate` (keep as duplicate; record becomes selectable again only if original request FAILED/DELETED).

## 7. Bugs, dead code, duplication, surprises

1. `_process_request_once` source-duplicate block (request_processing_pipeline.py:206-221): the second `if source_duplicate and not duplicate_candidate_is_current_book(...)` re-check after the claim path is redundant but also changes behaviour: when `_claim_unlinked_source_book` returns True the book becomes the request's linked_book (so current), fine; when False the first branch already returned. The second branch is effectively dead.
2. `_finalize_processing_request` PAUSED branch saves `{scrapedData, linkedBookId}` but not `curatedResult`; resume then gets scraped_data but `_saved_curated_result_for_resume` returns None, so `curated_result is None` triggers a full re-scrape (the `elif scraped_data is None` path is therefore rarely hit). Pause after scrape (RA-07) saves both; inconsistent.
3. `_apply_multi_page_toc_signal` is called before the PAUSED check but after the DELETED check; ValueError from toc_incomplete is raised for a PAUSED request and `_fail_processing_request` no-ops, so paused requests silently lose the failure.
4. `CONTENT_INCOMPLETE_RETRY_DELAY` uses blocking `time.sleep(60)` twice in the worker (up to 120 s), the stale threshold is 20 min and heartbeat only runs during scraping, not during the sleep (heartbeat stops after curate). Fine, but it blocks the single worker.
5. The "source site" substring in an error message controls retry behaviour (string-typed control flow); `startswith("Incomplete scrape:")` likewise.
6. `scrape_book.__module__ != "apps.processing.source"` hack detects monkeypatched legacy function (test seam in production code); legacy path skips heartbeat/page cache and skips review gating.
7. `_mark_request_review_required` stores FAILED with linked_book while book persisted without exports; `progress` is overwritten by validation info (not a checkpoint dict) and `processing_request_details` shows it as "" because no `checkpoint` key.
8. `apply_request_action` swallows unknown actions silently; no transaction; one failing request aborts the loop after earlier ones were committed; `sync_records_for_requests(changed)` is skipped on exception.
9. `apply_new_edition_action` reads `processing_request.submission`, which is a legacy ingestion submission concept (`persist_*_book(submission_stub, None, ...)` passes None submissions) – likely always None, so `target_book_group_id` is never written and the BookGroup is created but not wired to the new book (feature likely non-functional). Also BookGroup is created even when no submission exists.
10. `apply_confirm_duplicate_action` publishes domains with before=after DUPLICATE (`previous_state` ignored), so the old state's card (e.g. FAILED) may not be refreshed.
11. `ensure_processing_ui_rows` recomputes all shared payloads (including summary aggregation queries) on every call, and `rebuild_processing_ui_state` calls it each time before recomputing the requested subset: every domain publish runs summary queries twice, inside on_commit.
12. `publish_processing_ui_domains` is called while a request row may still be inside a transaction only because `on_commit` defers; `_transition_request_state` calls it inside `transaction.atomic()`, OK.
13. `next_request_id` check-then-act race; `request_blocks_record_selection` returns the request object or None (truthy typing sloppy).
14. `_scrape_heartbeat` updates `updated_at` only when state is PROCESSING; `queue_processing_request` for invalid URL calls `_fail_processing_request` which may leave state INITIAL -> FAILED without publishing if PAUSED.
15. Live catalog sync cannot be interrupted mid-fetch (pause waits for the whole `refresh_catalog_parallel`); `begin_catalog_request_creation` then immediately falls through to `finalize_catalog_sync` in the same call (sync_runner.py:194-199): after begin_catalog_request_creation sets status SYNCING/phase running, the code checks `state.status not in SYNC_ACTIVE_STATUSES` (false) and then calls `finalize_catalog_sync`, which marks the sync phase completed and request_creation phase NOT_STARTED, status IDLE. Unless `begin_catalog_request_creation` path is picked up by another call (dispatch) – as written, request creation seems immediately overwritten. Needs verification against `finalize_catalog_sync` semantics: `catalog_progress_after_completion(request_creation_phase_status=NOT_STARTED)` would set request creation to not_started and IDLE. This looks like a real bug or a flow where the automation path relies on a re-dispatch that is not visible here (flag for the other agent / planning).
16. `stop_sync` does not revoke Celery task nor clear counts; `task_id` cleared so the worker task is ignored via the task-id guard (ownership token pattern).
17. `fail_sync` and `stop_sync` leave `remote_pages` untouched.

20. Fragment files with no imports/leading blank lines are concatenated (exec-style) into one namespace: the rebuild must not copy this pattern.
21. Naming/message duplication: sync pause progress built in three places; the "Saved progress for N records before pausing" block duplicated twice in `advance_incomplete_sync_once`; the whole page-of-ids vs page-of-dicts branches duplicated.
