### 2.2 The only DB-level triggers: migration 0004 (processing_state_consistency_triggers.py)

1. 3. ### 2.4 Domain versions and projection rebuild (ui_domain_versions.py)
- `publish_processing_ui_domains(domains)` (:~78-100): normalises to known card keys, sorted; computes the shared-projection keys they depend on (`PROCESSING_SHARED_PROJECTION_DEPENDENCIES`, constants :193-204 - note `catalog-sync` depends on {catalog-sync, catalog-automation}; others self); plans versions into a context-var collector (`_plan_processing_ui_versions`: current DB version + 1, so the HTTP response can return the NEXT version before commit); then registers `transaction.on_commit(commit)`.
- `commit()`: (a) `rebuild_processing_ui_state(keys=projection_keys)` OUTSIDE its own atomic block and (b) `with transaction.atomic(): _bump_processing_ui_domains(domains)` which `bulk_create(..., ignore_conflicts=True)` missing version rows, then `SELECT ... FOR UPDATE ORDER BY domain` and `version = version+1` per row via `.save` (read-modify-write under row lock; ordered to avoid deadlocks), then merges results into the collector.
- Ordering consequence: the projection payload is rebuilt BEFORE the version is bumped, so a client that sees the version bump always reads the new projection. Good. But the projection rebuild is not atomic with the data commit (on_commit runs after commit) and not with the bump: if the process dies between commit and on_commit callback (or the callback raises), the data changed but versions never bump and the UI never refreshes until some other change; no repair job re-bumps (NOT READ: any periodic reconcile; none found in the files I read).

The full summary is recomputed even when only one overview card is requested (`requested_key_set & {overview...}` computes everything, ui_projection_queries `processing_shared_projection_payloads`).

## 3. SSE trace (view_modules/read_stream_and_sync_start_views.py)

- Endpoint class `ProcessingStreamView` (:162-204). Permission `CanManageProcessing` (:163). Query param `page` must be a key of `PROCESSING_PAGE_DOMAINS` (catalog, create, on-hold, incomplete, multipage, empty-chapters; constants :~241-275) (:102-106, :167).
- NO Redis. NO pub/sub. Per connected client the generator (:172-198): emits `event: connected`, reads the version map for the page's domains from `ProcessingUiDomainVersion` (:174), then loops forever: `time.sleep(1)` (:178, poll_interval_seconds=1 at :169) -> `processing_ui_versions_diff` (one DB SELECT of the page's domains per second per client, ui_projection_queries `processing_ui_versions_map`) -> if any version greater than last seen emit `event: versions` with `{eventId: ms-timestamp, versions:{domain: version}}` (:183-191); otherwise `: keepalive` comment every 15 s (:192-196). Only exits on `GeneratorExit` (:197).
- Consequences: (1) one blocked WSGI/thread worker per open tab, forever (sync generator + sleep), (2) 1 DB query/s/client, (3) delivery is at-most-once per diff but state-based: the client only learns "domain X is now at version N"; on reconnect it re-reads current versions (`last_versions` starts from current, so changes between disconnect and reconnect are NOT replayed - the client must refetch state on (re)connect; frontend behaviour NOT READ). (4) No `Last-Event-ID` handling, `eventId` is wall-clock ms and never used for resume. (5) Versions are monotonically increasing integers, so lost events are self-healing on next change; a client that never refetches after reconnect would drift.
- API shapes consumed by the UI: `GET state` (`ProcessingStateView` :133-143, `includeLists` default True returns every record and every request unpaginated: `serialized_processing_records()`/`serialized_processing_requests()` processing_state_queries.py:348-372, a full-table dump), `GET card?card=` for the 7 shared cards -> stored projection payload + `version` (processing_card_payloads.py:398-405), `GET table?card=&q=&category=&status=&offset=&limit=&includeFacets=` for table cards -> rows + pagination + filters + `version` (:117-310; limit max 600 :230 in constants / view clamps 1..600 :226-231), POST mutation responses return `{ok:true, versions:{domain:nextVersion}}` (`processing_mutation_payload` :109-120, `collect_processing_ui_version_updates` :254) so the actor's own UI can mark versions as already seen.
- Mutation response versions are PLANNED versions (current+1 computed before commit, ui_domain_versions `_plan_processing_ui_versions`), then replaced by actual post-commit versions when `commit()` runs; if the HTTP response is serialised before on_commit completes (they normally run synchronously at transaction end in ATOMIC_REQUESTS or autocommit) the planned and actual numbers can diverge under concurrency (two concurrent mutations plan the same N+1; DB assigns N+1 and N+2). Minor.

## 4. Change-propagation walk-through (single request state change, e.g. queued -> processing)

(Partly inferred from helper functions; the specific pipeline function bodies were not read, see Not read.)
1. App code (worker callback or action) sets `BookCreationRequest.state = processing` and saves.
2. DB trigger (AFTER UPDATE OF state) runs `processing_sync_book_record_state(book_record_id)` -> `UPDATE processing_bookrecord SET book_creation_state='processing', updated_at=NOW()` (only if different). That UPDATE fires the BEFORE trigger on bookrecord, which re-derives the same value (idempotent; no recursion since the AFTER trigger is on the request table, not the record table).
3. App calls `sync_record_state(record)` (usually a no-op by now, or a save that the BEFORE trigger normalises).
4. App calls `publish_processing_ui_domains(processing_domains_for_request_change(before_state, after_state, record=record))` -> domains = catalog-overview, catalog-records, multipage-records, create-queue, create-processing, create-overview (+ incomplete-* if applicable). Collector gets planned versions. `on_commit` registered.
5. Transaction commits. `commit()`: rebuild shared projections for catalog-overview and create-overview (full summary recompute: ~10 COUNT queries), then in a new atomic block bump the version rows (SELECT FOR UPDATE, +1, save) for each domain.
6. Every SSE client polls version rows each second; those whose page includes a changed domain get `event: versions`. The frontend then (not read) refetches the affected card/table via `/card` or `/table`.
7. Table content (rows) is never cached: rows come from live queries on `BookCreationRequest`/`BookRecord`, so tables are always consistent with the DB at fetch time; only the 7 shared overview/sync/automation cards are stored projections and can be stale.

Rows changed for one transition: 1 BookCreationRequest, 1 BookRecord (via trigger), 2-N ProcessingUiProjection rows (rewritten), ~6-8 ProcessingUiDomainVersion rows. Write amplification: ~10 row writes + ~10 aggregate COUNT queries per transition.

## 5. Where drift can happen (so far)
- (D1) App crash/exception between data commit and `on_commit` callback or inside `commit()` (rebuild raises after commit): data new, projection/version old; no reconciler found.
- (D2) `rebuild_processing_ui_state` runs outside the version-bump transaction; two concurrent commits can each rebuild then bump; last rebuild wins, but each rebuild reads current data so the final projection is not stale unless an interleaving writes older data last (rebuild A reads before change B commits, writes after B's rebuild) - possible lost update of projection (A overwrites B's fresher payload) because `update_or_create` has no versioning. Window is small but real.
- (D3) Anything that writes `BookCreationRequest`/`BookRecord` via paths that do not call publish (admin, shell, queryset `.update()` that bypasses signals, migrations, ingestion engine writing ProcessingJob/BookCreationRequest directly): trigger keeps record state consistent but UI versions do NOT bump.
- (D4) `empty-chapters-records` not in request-change domain sets (see 2.5).
- (D5) Planned vs actual versions in mutation responses.
- (D6) Two implementations (Python + SQL) of the "latest request wins" rule; tie-breaking identical in text (updated_at DESC, created_at DESC, id ASC), but Python orders by prefetched cache which may be stale.

## 3b. Jobs SSE (ingestion/views/jobs.py `ProcessingJobStreamView`)
Different mechanism from the processing page SSE: opens a dedicated Redis connection per client, `SUBSCRIBE` to CH_JOB_ASSIGNED, CH_JOB_COMPLETED, CH_JOB_REASSIGNED, loops `get_message(timeout=5)`; every message becomes `event: job-update` with raw engine payload; on timeout emits `: keepalive`. Events are fire-and-forget (no replay); a client that connects late gets nothing historical; messages carry only job_id/worker/status so the UI must refetch job lists (UI side NOT READ). No Redis error handling inside the generator (exception ends the stream; client must reconnect). This is the only Redis-pubsub-to-browser path I found; the processing console uses DB polling instead.

### 5.1 Registration
- Each Celery pool child process runs `on_worker_process_init` (signals.py:183-195): publishes ONE `CH_WORKER_REGISTER` message {hostname, capabilities, pool_size=1, concurrency=1} via PUBLISH and starts two daemon threads (assignment listener, heartbeat). Hostname = `celery-{socket.gethostname()}-{pid}@worker` (signals.py:47-56). Capabilities are a hard-coded list of five strings (signals.py:189), identical for every worker, including `catalog_sync`, `curation`, `automation` which the listener has no branch for (signals.py:146-153 handles only `process_submission` and `pipeline`; else logs warning and STILL publishes `done: succeeded` at :155-163).
- Engine side `_handle_worker_register` (engine.py:131-146): `register_worker` writes hash `engine:worker:{hostname}` with HSET x8 (worker_registry.py:17-27; non-atomic, 8 round trips; no TTL; status=idle; current_job=""), then `_dispatch_pending_jobs()`.
- Registration is a single fire-and-forget pub/sub message. If the engine is down, Redis restarted or the subscriber is not yet subscribed, the message is lost permanently. The heartbeat loop does not re-register (see 5.2). `update_heartbeat` returns False if the key is missing (worker_registry.py:43-45) and nobody reacts.
- Pool-child recycling (`max_tasks_per_child=50`, `max_memory_per_child`): each respawn is a new pid -> new hostname -> a new worker key. The OLD key remains (no TTL), is eventually marked stale by the detector and never deleted (stale marks, only recovery marks OFFLINE; nothing removes keys except `deregister_worker`, which only runs if the shutdown signal handler runs). So `engine:worker:*` accumulates dead entries with each recycle; `find_idle_worker`/`get_all_workers` cost grows (N+1 HGETALL via SCAN, worker_registry.py:80-94).

### 5.2 Heartbeats
- Worker side: `_heartbeat_loop` thread publishes {hostname,timestamp} to `CH_WORKER_HEARTBEAT` every 5.0 s (signals.py:78-88), independent of job execution (the job runs in the listener thread). `_publish` swallows all exceptions (signals.py:~70-76). Additional senders: Celery `heartbeat_sent` signal (signals.py:218-225) which fires in the Celery main (parent) process whose `os.getpid()` differs from the pool child, so it publishes heartbeats under a hostname that was never registered (harmless no-ops because update_heartbeat returns False for unknown keys, but it proves two parallel heartbeat systems), and `task_prerun` publishes a heartbeat with extra `job_id/status` fields that the engine ignores (engine.py:148-152 reads only hostname).
- Engine side: `update_heartbeat` HSETs `last_heartbeat` and, if status==stale, flips it to idle (worker_registry.py:43-52) - even if the worker is actually mid-job (see F-6).
- Stale detection: separate thread every `heartbeat_check_interval`=2 s (engine.py:120-129; constants.py:3-4: timeout 15 s). `check_stale_workers` (stale_detector.py:14-51) reads every worker, skips OFFLINE (:26), computes `now - last_heartbeat` (parse failure -> elapsed=0, i.e. unparseable never goes stale, :35-38), if > timeout: set STALE, PUBLISH `CH_WORKER_STALE`, then for each ACTIVE_JOBS entry owned by the worker: `unassign_job`, `enqueue_job` (RPUSH to the BACK of the queue, not front; `requeue_job` which does LPUSH exists but is not used), PUBLISH `CH_JOB_REASSIGNED`. A STALE worker is not skipped on later passes (only OFFLINE is), so every 2 s it is re-marked, `CH_WORKER_STALE` re-published and `_dispatch_pending_jobs` re-run (engine.py:126-127). Nothing ever moves STALE -> OFFLINE except engine restart recovery, so a dead worker generates an event every 2 s forever.

### 5.3 Choosing an idle worker
- `find_idle_worker(redis, required_capability)` (worker_registry.py:97-109): `get_all_workers` = SCAN `engine:worker:*` + HGETALL per key + JSON-decode capabilities; returns the FIRST worker whose `status == idle` and whose capability list contains the handler. Order is SCAN order (effectively arbitrary but stable); no least-loaded/round-robin; ignores `last_heartbeat` (a worker that died <15 s ago is still "idle" and can be selected); ignores `pool_size`/`concurrency` (always one job per worker).
- Handler for a job comes from hash `engine:job:handlers` (HSET in `dispatch_job` dispatch.py:14 and `_handle_job_request` engine.py:195); missing entry defaults to "process_submission" (engine.py:229) - after a Redis wipe a pipeline request would be dispatched with the wrong handler unless recovery step 4 re-populated it.
- `_dispatch_pending_jobs` (engine.py:220-260): loop { LINDEX queue 0; look up handler; find idle worker; if none -> break (head-of-line blocking: one job needing a capability with no idle worker blocks all jobs behind it, though all workers have all capabilities today); LPOP; sanity-check popped == peeked (else LPUSH back and break); `assign_job` (HSET ACTIVE_JOBS job->worker, set worker current_job, set status=processing - three separate writes, not atomic); PUBLISH `CH_JOB_ASSIGNED`; best-effort DB update of `ProcessingJob.worker_hostname` (UUID ids only; `BookCreationRequest` ids that are not UUIDs are skipped, engine.py:262-274) }.
- `_try_assign_job` (engine.py:201-218) is defined but never called (no references in the files I read: UNUSED / dead code). `ENGINE_POLL_INTERVAL` (constants.py:7) has no use in the files I read.
- Concurrency inside the engine: event-loop thread AND stale-check thread both call `_dispatch_pending_jobs` (engine.py:127 vs :144,:183,:199); the comment "engine is single-threaded" at engine.py:242 is false. The LINDEX/LPOP guard mitigates but two threads can both see the same idle worker before either writes `status=processing`, so one worker can receive two assignments (the second is buffered behind the first in its listener, i.e. executed serially later).

### 5.4 Assignment delivery and job execution on the worker
- Engine PUBLISHes `CH_JOB_ASSIGNED` {job_id, worker_hostname, handler} (engine.py:252-255). Every worker's listener thread (signals.py:121-180) is subscribed (its own Redis connection, `get_message(timeout=1.0)`), ignores messages whose `worker_hostname != own hostname` (:140), then runs the handler SYNCHRONOUSLY in the listener thread: `process_submission_job(job_id, retry_count=0, task_id="engine")` (note: retry_count hard-coded 0 so the retry counter is not carried) or `kickoff_request_processing(job_id)`; then PUBLISHes `CH_WORKER_DONE` succeeded/failed.
- There is NO acknowledgement of assignment, NO per-job lease/timeout in the engine, and the engine learns about success only through `CH_WORKER_DONE`.
- Completion: `_handle_worker_done` (engine.py:160-185): `unassign_job` (clears ACTIVE_JOBS entry and, if current_job matches, worker status->idle), HDEL handler entry, set the reporting hostname idle and current_job "" unconditionally, PUBLISH `CH_JOB_COMPLETED`, update `ProcessingJob.status/finished_at/last_error` directly with `.update()` (bypasses model save and signals), then dispatch more. Done for a job id also arrives from the Celery `task_postrun` signal for ANY Celery task whose first positional arg exists (signals.py:242-264), with hostname = pool child; for non-engine tasks this sets that worker idle while its listener thread may be running an engine job, and writes `ProcessingJob` status when the arg happens to be a UUID of a job.

### 5.5 Engine restart (recover_state, called once in `start()`, engine.py:52; recovery.py:14-99)
Order: recover_state -> `_dispatch_pending_jobs` -> subscribe -> threads. Steps:
1. For every worker whose recorded status is OFFLINE or STALE: set OFFLINE, requeue its active jobs (RPUSH back of queue) and publish REASSIGNED (recovery.py:27-41). Workers whose status is idle/processing are trusted regardless of `last_heartbeat` (the variable is read at :31 and unused).
2. ACTIVE_JOBS entries whose worker key no longer exists -> unassign + requeue (recovery.py:43-50).
3. DB sweep (recovery.py:52-94) inside one big try/except that swallows everything and logs: `BookCreationRequest` in QUEUED/PROCESSING that are neither in the Redis pending list nor in ACTIVE_JOBS -> if PROCESSING revert to QUEUED (direct `.save(update_fields=[state, updated_at])`, no `_transition_request_state` CAS and NO `publish_processing_ui_domains` call; the SQL trigger fixes the record state but UI versions do not bump -> drift D3), set handler "pipeline", RPUSH to queue. Same for `ProcessingJob` queued/processing -> queued, handler "process_submission". Also note: no check for `cancel_requested`, no respect for `PROCESSING_DISPATCH` markers, and no cap on attempts (each engine restart resets a job that crashed the worker into the queue again: poison-job loop through restarts).
4. The recovery is a startup-only step; it is not a periodic reconciler. Redis<->DB reconciliation after startup is done only by the Celery-beat layer (2.8) at 1/min granularity.
- Redis pub/sub messages sent while the engine is down (register, heartbeat, done, job_request) are dropped. Queue pushes by `dispatch_job` (RPUSH + HSET) survive in Redis (subject to persistence), so queued work is picked up by the start-up `_dispatch_pending_jobs()` call at engine.py:54.
- After a downtime longer than 15 s, all workers' `last_heartbeat` are older than the timeout; first stale pass runs 2 s after start (engine.py:123 sleeps first), workers heartbeat only every 5 s, so up to a ~5 s window where LIVE busy workers are declared stale and their running jobs requeued (F-3).
- `JobEngine.stop()` (engine.py:79-97) unsubscribes and joins the loop; it does not wait for / hand over in-flight dispatch. `__main__.py` and `run_engine.py:32-60` install SIGINT/SIGTERM handlers that call `engine.stop()`, `redis.close()`, `sys.exit(0)`.

### 5.6 Redis restart / loss
- Engine: `_event_loop` catches exceptions from `get_message` and `continue`s immediately with no sleep or backoff (engine.py:104-111); with `socket_timeout=5` (redis_client.py:12-26) each failed attempt blocks up to 5 s, so it is a slow spin with log spam, not a hot loop. Whether redis-py transparently reconnects and re-subscribes its channels after a dropped connection is a library behaviour I did not verify.
- Worker listener thread: `_engine_listener_loop` has `try/finally` but NO `except` around `get_message` (signals.py:121-180, only JSON decode and handler errors are caught inside the loop). Any redis `ConnectionError`/`TimeoutError` raised by `get_message` terminates the thread (finally closes pubsub and client). `_engine_listener_running` stays True, `_engine_listener_thread` is not None, so `_start_engine_listener` never restarts it (signals.py:91-95), while the independent heartbeat thread keeps publishing successfully once Redis is back. Result: a "zombie" worker that appears alive and idle/processing but never runs any assignment (F-1). (Assumes redis-py raises on connection loss rather than recovering internally; unverified.)
- If Redis comes back with data (RDB snapshot) the worker hash/queue/ACTIVE_JOBS are as of the last snapshot; if it comes back empty, all worker keys vanish and nothing re-creates them (F-2).

## 8. Keep / change / drop for a rebuild

Keep (as concepts)
- Monotonic per-domain version counters + state fetched by version: self-healing, simple contract (a client only needs "domain X changed", then refetch). Keep a version per queryable view, bump in the SAME transaction as the data write (outbox style) instead of `on_commit`.
- The invariant "record-level state is a pure function of its latest request" enforced by the database (trigger or, better, computed view / generated read model) so no code path can violate it.
- Compare-and-set state transitions with row lock (`_transition_request_state`).
- Heartbeat-based liveness of workers; bounded retries (`MAX_ATTEMPTS`) and time-based DB stale sweeps as a safety net.
- Idempotent re-dispatch marker idea (`_dispatchRequestedAt` with a window).

Change
- Replace pub/sub with durable job state: jobs live in Postgres (or Redis streams with consumer groups / ack) with `status`, `lease_owner`, `lease_expires_at`, `attempt`; workers claim with `SELECT ... FOR UPDATE SKIP LOCKED` and renew the lease; recovery = expire lease -> re-queue. This removes: worker registry, idle-worker selection, ASSIGNED/DONE/REGISTER/HEARTBEAT messages, S1/S5/S6/S7/S8/S9/S10/S11/S13 failure classes.
- If a registry stays: workers re-register on every heartbeat (idempotent upsert with TTL), registry entries expire by TTL.
- Make handlers idempotent and keyed (request id + attempt) so duplicated delivery is harmless; guard `run` with the state CAS (only the transition winner runs).
- One recovery authority and one clock: unify engine sweep and beat sweeps; run the reconciler periodically, not only at startup.
- Projection updates in the write transaction (or transactional outbox row consumed by a single publisher); include all domains in one mapping table (data, not code) so no domain (e.g. empty-chapters) is forgotten; add a periodic "recompute all counts and compare/bump" job.
- Replace per-client DB polling SSE with a single fan-out (Postgres LISTEN/NOTIFY or Redis pub/sub in one process) and Last-Event-ID replay of versions; async server so connections do not hold threads.
- Paginate/limit `GET state`; summary counts via grouped queries or maintained counters.

Drop
- exec-composed module namespace; dual Celery-signal + listener-thread completion paths; `reassign_job`, `_try_assign_job`, unused channels (REASSIGNED/COMPLETED/STALE unless a consumer is specified); static unimplemented capability strings; inline fallback execution inside web requests; `primary_sync_payload` heuristic in the backend (make explicit scope in the API).
