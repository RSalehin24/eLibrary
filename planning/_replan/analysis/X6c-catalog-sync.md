## 4. Phase 2 trace (request creation) and the sync_runner.py 194-199 claim

Real-world call sequence (live mode, automated run), as traceable in code:
1. Beat (every minute, celery.py:35-38) -> `run_due_processing_automations` -> `run_catalog_automation` -> `start_sync(live)` -> Celery `run_processing_sync_task` (tasks.py:17-23) -> `run_processing_sync_until_blocked` -> `refresh_catalog_parallel` (long crawl).

After crawl: `begin_catalog_request_creation` flips the row to SYNCING/request_creation and saves (observable UI flicker via SSE), then `finalize_catalog_sync` immediately sets it IDLE, request_creation NOT_STARTED. The Celery task returns. NO request has been created in this task. `last_run_at` is not set.
3. Self-heal via scheduler: the next minute `automation_is_due` is still true (`last_run_at` unchanged, automation_commands.py:76-107) -> `run_catalog_automation`: state IDLE, no conflict; no paused rc; not active; sync phase COMPLETED and rc NOT_STARTED matches (automation_commands.py:184-189) -> calls `begin_catalog_request_creation(sync_state)` again, which sets SYNCING with `task_id=""` and does not dispatch.
4. `run_processing_runtime_tick` (every 60 s, celery.py:31-34; maintenance_and_request_actions.py:165-176) sees an active state with empty task id -> `advance_sync_once` (sync_runner.py:205-212) -> `run_processing_sync` -> phase == request_creation -> `advance_catalog_request_creation_once`: ONE batch of 50 records per tick. 5. When the last batch is processed `complete_catalog_automation` sets `last_run_at`.
Net effect: not "request creation never happens", but (a) the handoff is accidentally undone and recovered only through the 1-minute scheduler loop; (b) it only recovers while automation is still `enabled` and due - if the owner disables automation, or the schedule is not due (e.g. manual "Run now" outside schedule/after the day rolled), the state sits at sync=completed/rc=not_started with no requests created until the next due run, which then SKIPS re-syncing and goes straight to phase 2 on possibly stale data (automation_commands.py:184-189); (c) request creation is throttled to 50/min via the tick; (d) in non-live mode the same handoff works correctly because `advance_catalog_sync_once` returns the `begin_` state directly (automation_advancement.py: advance_catalog_sync_once lines in incomplete_catalog_fetch.py:174-176, :209-211) and the inline loop continues in `advance_catalog_processing_once` (sync_runner.py:143-152). ## 6. Incomplete-books trace

Purpose: source site publishes an "incomplete books" genre page; books on it are tagged `was_incomplete=True` with category "অসম্পূর্ণ বই". When a book leaves that list (author finishes it), the record is "resolved": category set to the real one.

Live listing fetch (incomplete_catalog_fetch.py:76-143): GET `INCOMPLETE_CATALOG_URL` for page 1, `.../page/N/` for N>1 (catalog_record_sync.py:219-222), parse anchors `.entry-title a[href], article h2 a[href], article h3 a[href]` (:3-38) keeping only normalisable source URLs. Page N>1 returning 404 = end of archive (:85-94). For each entry it fetches the book's own page to find the real category (`incomplete_resolution_category`: first non-incomplete value among willResolveToCategory/.../category/book_type, :41-55), writes `raw_data` with `willResolveToCategory`, and upserts a `SourceCatalogEntry`; payload sets `category="অসম্পূর্ণ বই"`, `wasIncomplete=True`, `resolvedFromIncomplete=False`, `willResolveToCategory` (:58-73). Metadata fetch failure falls back to listing metadata with empty `willResolveToCategory` (:119-134). `fetch_live_incomplete_remote_pages` (up to 250 pages, dedup + repeating-page signature break, pages of 100 + `[]` terminator, :146-180) is used at start_sync/resume (non-incremental) when workers are available; the live incremental path `advance_live_incomplete_sync_once` (incomplete_resolution.py:107-168) fetches ONE page per task step (page_number = page_index+1, up to no cap), upserts the records (incomplete flags reset), saves progress, honours pause per page.

Resolution: after the listing is exhausted (empty or repeated page) `complete_live_incomplete_sync` (incomplete_resolution.py:100-104) computes `stale_incomplete_record_ids`: every unresolved incomplete BookRecord (`resolved_from_incomplete=False` and (`was_incomplete` or category contains an incomplete keyword), automation_advancement.py:206-209) whose normalised URL is NOT in the URLs seen in this run (incomplete_resolution.py:86-97). `resolve_incomplete_records` (:3-53) for each: sets `category = preferred_incomplete_resolution_category` (will_resolve_to_category -> source entry raw_data -> existing non-incomplete category -> "Uncategorized", automation_advancement.py:250-261), `was_incomplete=True`, `resolved_from_incomplete=True`, `book_creation_state=CREATED` (!); the latest request is set to CREATED with progress cleared, or a CREATED request with origin automation is fabricated if none exists (:13-42). Then `complete_incomplete_automation` sets `last_run_at` and a "Updated N books" message (:56-69).

Snapshot (non-live) mode: `incomplete_automation_pages` = ids of unresolved incomplete records having non-empty `will_resolve_to_category`, in pages of 100 + `[]` (automation_advancement.py:189-203); `advance_incomplete_sync_once` (sync_runner.py:3-101) treats id-list pages by calling `resolve_incomplete_records(page)` directly - i.e. every record with a known target category is marked resolved with NO check against the live listing (:18-24). If there are zero such records, pages=`[[]]`, the first branch (:11-16) runs `stale_incomplete_record_ids(remote_pages)` where remote_pages holds no dicts, so `incomplete_remote_urls` is empty and EVERY unresolved incomplete record is considered stale and resolved.

Findings on this flow are in section 10. The resolved record does NOT trigger a re-scrape or book update; it only flips labels/state (the actual book content refresh for a completed book is not triggered here).

- `last_run_at` is written only on successful completion (catalog: automation_advancement.py:15-19; incomplete: incomplete_resolution.py:56-62). `fail_sync` (sync_completion.py:3-24) sets IDLE, `last_error`, message but not `last_run_at`.

## 8. Request actions trace

`ProcessingRequestActionView` -> `apply_request_action(ids, action, delete_book, actor)` (request_action_dispatch.py:251-281). Actions: `delete`, `pause`, `resume`, `retry`, `force_generate`, `new`, `new_edition`, `confirm_duplicate`, `create_again`/`recreate`; unknown actions are silently skipped with `continue` (:277-278) although the view expects `ValueError` (view :96-97) - serializer validation of the action list NOT READ. No precondition checks on current state for any action; none revokes an in-flight Celery task. After the loop records are re-synced (`sync_records_for_requests`).
- delete (maintenance_and_request_actions.py:179-197): state DELETED, progress/error cleared; optional `delete_book` soft-deletes linked book (`soft_delete`, NOT READ).
- pause (:200-219): state PAUSED, progress rebuilt keeping checkpoint (`_build_processing_progress` NOT READ). Does not stop a running worker.
- resume (:222-239): state INITIAL, `is_resumed=True`, `force_generate=False`, re-queued.
- retry (:352-390): INITIAL, clears force flag/error/progress/duplicate_confirmed; clears the record's duplicate flags; re-queue. (Progress=None means the checkpoint is thrown away; the disk scrape cache may still be used if it exists - wiring NOT READ.)
- force_generate (:303-349): same as retry but `force_generate=True`; docstring says the pipeline then bypasses the REVIEW_REQUIRED gate and applies auto-mitigations: strip source-chrome blocks and disambiguate duplicate content paths (helpers :245-300; call site NOT READ).
- new (request_action_dispatch.py:50-98): "this is not a duplicate": INITIAL, `is_confirmed_not_duplicate=True`, drops duplicate links and `linked_book` on both request and record; re-queue (the old Book is not touched here).
- new_edition (:30-47): resolves the existing duplicate Book (via `duplicate_of_request.linked_book` or `duplicate_of_record.linked_book`, :4-16), lazily creates a `BookGroup(canonical_title=existing.title)` and attaches existing book (:19-27), writes `target_book_group_id` into `submission.raw_payload` only if a submission exists and a group was found (:40-45), then runs `apply_new_action`. If no submission yet, the group link is silently lost (new book would be a plain new book).
- confirm_duplicate (:101-146): state DUPLICATE, `duplicate_confirmed=True`, link to the other request/record, mark record `is_duplicate`.
- recreate (:149-187): like retry, INITIAL.
- Bulk selection: `create_requests_for_record_ids` (automation_commands.py:34-42) only for records passing `record_is_selectable` (NOT READ), origin default curation; `ProcessingRecordCreateRequestsView` (view :63-79).
- Pipeline advance fallback `advance_pipeline_once` (request_action_dispatch.py:190-248), called each runtime tick: first `mark_stale_processing_requests`; moves at most ONE oldest QUEUED request (dispatch or inline), runs at most one PROCESSING manually if inline/no workers, and flips at most ONE oldest INITIAL to QUEUED per call; if nothing advanced, runs duplicate repair.

## 9. Maintenance / stale logic (20-minute rule)

`PROCESSING_STALE_AFTER = 20 min` (constants :143); runs every minute via `run_processing_maintenance` (maintenance_and_request_actions.py:154-162) and also via the runtime tick for requests (`advance_pipeline_once`).
- `mark_stale_processing_requests` (:76-96): requests in PROCESSING with `updated_at` older than 20 min -> transition to QUEUED (atomic helper `_transition_request_state`, NOT READ), error cleared, `is_resumed=True`, re-queued. Liveness depends on something touching `updated_at`; the constant `PROCESSING_SCRAPE_HEARTBEAT_INTERVAL = 300` s says scraping touches the row every 5 min (writer NOT READ). Attempt cap (`MAX_PROCESSING_REQUEST_ATTEMPTS = 3`) usage NOT READ here.
- `recover_stale_sync_states` (:99-151): ProcessingSyncState rows SYNCING/PAUSING with `updated_at` older than 20 min: PAUSING -> converted to PAUSED with a re-built checkpoint ("progress saved after interruption"); SYNCING -> message "Recovering interrupted ...", task id cleared, re-dispatched with `force=True` if workers exist (otherwise picked up by the runtime tick). Request-creation phase resumes from its saved `lastRecordId`; sync phase from `nextPageIndex`.
- `repair_self_linked_duplicate_requests` (:3-73): DUPLICATE requests that link to a live book but have no duplicate target -> set CREATED and fix record flags.
- Whether `updated_at` is `auto_now` (TimeStampedModel in apps.common.models) was NOT READ; the 20-minute rule assumes it is.

## 11. Keep / change / drop for a rebuild

Keep (concepts): a durable local mirror of source catalog entries separate from "books"; two-phase flow (mirror, then decide what to build) but modelled as two explicit jobs; per-request checkpointing with resumable scrape cache; idempotent upsert by URL; cooperative pause (checkpoint at page/batch boundaries); stale-lease recovery with an owner/lease token; the request action vocabulary (retry, delete, pause, resume, force-generate, new edition, confirm duplicate) with explicit allowed-transition table; "incomplete" tracking as a first-class record state; `origin` on requests.
Change: one job-run row per run with a lease (heartbeat updated by the worker during the crawl; stale only if heartbeat missed), a real page cursor persisted per page (even in "live" mode), and a single hand-off from fetch to request creation inside one transactional state machine (no IDLE bounce); `last_run_at`/attempt backoff written on every start and failure; automation runs must be mutually exclusive via DB lock/unique active-run constraint; request creation must be bounded (rate cap, backpressure) and filtered (skip incomplete, unsupported, previously deleted) with order = source order; per-fetch error accounting (retry then mark run partial, never silently skip pages); "resolve incomplete" must (a) refuse to run when the listing is empty/suspect (min count / % change guard), (b) mark "ready to (re)scrape" instead of CREATED, and (c) enqueue a refresh of the book; mirror should soft-mark records not seen in N consecutive full syncs. Stop must revoke/cancel the worker via the lease; request actions need state guards and cancel in-flight work; ownership between manual and automation should be an explicit lock with owner+reason, not inferred from progress JSON.
Drop: the dual legacy/phaseStates normaliser, Redis checkpoint mirror (unless it is the real store), `remote_pages` blob in the state row, pytest/eager special cases in production code, inline fallback when dispatch fails, the live-vs-snapshot split (snapshot mode only mirrors an already-filled table), per-request-mode flags that changed semantics by environment.
