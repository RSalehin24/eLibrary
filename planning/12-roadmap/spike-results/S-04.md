# S-04 result: EPUB samples, epubcheck, Java image and model tools

Status: DONE (2026-11-20). Throwaway scripts are in [S-04/](S-04/) (standard library only; not product code, the Rust builder replaces them in P6).

## epubcheck 5.4.0 (D-68) on hand-built EPUB 3 samples

`build_samples.py` assembles a valid sample (OPF, nav and NCX, XHTML in Bengali, CSS, PNG cover, embedded Noto Sans Bengali) and five broken variants. `measure.py` runs a command and reports exit code, wall time and peak memory.

| Sample | Exit | Errors | Time | Peak memory (heap 512 MB) |
|---|---|---|---|---|
| valid | 0 | 0 | 1.8 s | 469 MiB |
| missing nav | 1 | 1 | 1.8 s | 476 MiB |
| missing manifest file | 1 | 1 | 1.9 s | 482 MiB |
| malformed XHTML | 1 | 1 | 1.9 s | 477 MiB |
| no `dc:language` | 1 | 1 | 1.9 s | 482 MiB |
| **`mimetype` entry compressed** | **0** | **0** | 1.9 s | 493 MiB |

Large input: 29 MB, 300 chapters, 30 MB image: exit 0, **2.5 s, peak 354 MiB with `-Xmx256m`** (467 MiB with 512 MB).

**Finding:** epubcheck 5.4.0 accepts a compressed `mimetype` entry (OCF requires it stored uncompressed). Our own EPUB audit (`domain-builders`, planned) must check that and the entry order itself; the publish gate cannot rely on epubcheck for it.

## Java runtime image (D-47)

`epubcheck-image.Dockerfile`: `debian:trixie-slim` (119 MB) plus `openjdk-21-jre-headless` and epubcheck gives **543 MB**. It validates the valid sample (exit 0) and fails the broken one (exit 1) inside a container limited to **384 MB**, read-only root, `-Xmx256m`. Open for P6: the image is large; a smaller runtime (jlink) is possible but needs a JDK build stage and is not decided. Suggested worker `mem_limit` while epubcheck runs: 768 MiB (JVM 354 MiB plus the Rust pipeline), provisional until P6.
